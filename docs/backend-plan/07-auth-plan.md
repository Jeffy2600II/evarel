## 1. ข้อเท็จจริงที่ชนกับข้อ 3 (ต้องรู้ก่อนลงมือ)
- Supabase **ผูก identity อีเมลเดียวกันอัตโนมัติ และไม่มีสวิตช์ปิด** (ปรับได้เฉพาะ manual linking) -> ข้อ 3 ทำด้วยค่าตั้งอย่างเดียวไม่ได้ ต้องมีชั้นป้องกันของเราเอง
- กลไกในตัวของ Supabase: ผูกเฉพาะเมื่ออีเมลเดิม**ยืนยันแล้ว** ถ้าไม่ยืนยันจะ**ลบ identity ที่ยังไม่ยืนยันทิ้ง** = พฤติกรรมที่ Master ห้าม
- ข้อ 3 จึงสำเร็จได้จากการ "ไม่ปล่อยให้เกิดสถานะอีเมลยังไม่ยืนยันที่ชนกับ Google" ผ่านชั้นป้องกัน §2

## 2. ชั้นป้องกันข้อ 3 (ออกแบบ)
**หลัก:** บัญชีหนึ่งอีเมลมีตัวตนเดียว และไม่มีบัญชีอีเมล "ค้างยังไม่ยืนยัน" ให้ Google ไปชน
1. **สมัครอีเมลต้องผ่านขั้นยืนยันก่อนสร้างผู้ใช้จริง** (ดู §4) บัญชีรหัสผ่านที่ยังไม่ยืนยันจึงไม่ปรากฏเป็นผู้ใช้ใน `auth.users`
2. **Before User Created Hook** (Postgres function ของ Supabase) ตรวจก่อนสร้างผู้ใช้ทุกครั้ง: ถ้าอีเมลมีผู้ใช้ที่ยืนยันแล้ว (provider ต่างกัน) ให้**ปฏิเสธการสร้าง**พร้อมรหัสข้อผิดพลาดของเราเอง (`needs_link`) แล้ว UI พาไปขั้นยืนยันตัวตนเดิม แทนการผูกเงียบๆ
3. **ทางเข้า Google ชนอีเมลที่มีรหัสผ่านอยู่แล้ว:** ไม่ผูก ไม่ลบ แจ้งผู้ใช้ "อีเมลนี้มีบัญชีอยู่แล้ว เข้าสู่ระบบด้วยรหัสผ่านก่อน แล้วเชื่อม Google ที่ตั้งค่า" (ใช้ `linkIdentity` ที่ต้องล็อกอินอยู่ = มนุษย์ยืนยันเอง)
4. **ผู้ใช้ Google ล้วน:** ไม่ถูกบังคับตั้งรหัสผ่านหรือยืนยันซ้ำ (Google ยืนยันอีเมลให้แล้ว) เพิ่มรหัสผ่านทีหลังได้ใน "บัญชี" ผ่าน `updateUser`
5. **ตอบแบบไม่เปิดเผยว่าอีเมลมีอยู่** ที่หน้าสมัคร/ลืมรหัส (กันเดาอีเมล) เว้นแต่ผู้ใช้พิสูจน์ตัวแล้ว
> ความไม่แน่นอนที่ต้องทดสอบจริงก่อนไว้ใจ: พฤติกรรมของ hook เมื่อ identity ที่สองมาจาก OAuth ว่า hook ถูกเรียกหรือไม่ ผมจะทดสอบกับโปรเจกต์จริงในเฟสต่อ Supabase **ไม่เชื่อเอกสารอย่างเดียว** และถ้าชั้นนี้กันไม่ได้ จะแจ้ง Master ก่อน ไม่ปล่อยผ่าน

## 3. สวิตช์ "เตรียมไว้แต่ยังไม่ใช้" (ข้อ 1)
- ตัวแปรเดียว `REQUIRE_EMAIL_VERIFICATION` (ค่าเริ่มต้น `false`) อยู่ที่ Worker + ปิด/เปิด "Confirm email" ใน Supabase ให้ตรงกัน
- `false`: สมัครแล้วเข้าได้ทันที (เหมือนเดโม) **แต่หน้ากรอกรหัส/หน้า "ตรวจอีเมล" สร้างและทดสอบครบแล้ว ซ่อนอยู่หลังสวิตช์**
- `true`: เปิดใช้เมื่อมีโดเมน + Resend พร้อม ไม่ต้องแก้โค้ด
- ข้อควรระวัง: ขณะ `false` ชั้นป้องกัน §2 ข้อ 1 ยังไม่ทำงานเต็ม (บัญชีไม่ได้ผ่านยืนยัน) จึงกำหนด**ห้ามเปิดแอปให้คนอื่นสมัครสาธารณะจนกว่าสวิตช์เป็น `true`** ตอนนี้ใช้ส่วนตัวของ Master คนเดียวเท่านั้น

## 4. ลำดับสมัครอีเมล (เมื่อสวิตช์ true)
สมัคร -> ส่งอีเมล 1 ฉบับมี**ทั้งลิงก์และรหัส 6 หลัก** -> ผู้ใช้กดลิงก์ หรือพิมพ์รหัสในแอป -> ยืนยันสำเร็จจึงได้ session
- รหัสหมดอายุ 10 นาที | ขอใหม่ได้ทุก 60 วินาที (ตรงปุ่มนับถอยหลังในเดโม `RESEND_SEC`) | ผิดเกิน 5 ครั้งต้องขอใหม่
- ใช้เทมเพลตเมลของ Supabase ที่ใส่ทั้ง `{{ .ConfirmationURL }}` และ `{{ .Token }}` ในฉบับเดียว
- ภาษาไทย ชื่อผู้ส่ง Evarel | เนื้อหาสั้น ไม่มีรูปหนัก

## 5. การส่งอีเมล (Resend)
- ทางที่เลือก: **SMTP ของ Resend ต่อเข้า Supabase** (host smtp.resend.com พอร์ต 465 user `resend` pass = API key) ไม่เขียนโค้ดส่งเมลเอง
- เงื่อนไข: ต้องมีโดเมนที่ยืนยัน DNS (SPF/DKIM) | ฟรี 100 ฉบับ/วัน ใช้พอสำหรับผู้ใช้ส่วนตัว
- **ยังไม่ทำจนกว่า Master มีโดเมน** ระหว่างนี้ SMTP ในตัวของ Supabase ส่งได้เฉพาะอีเมลสมาชิกทีมโปรเจกต์ (ใช้ทดสอบกับอีเมล Master เองได้)

## 6. Google (ข้อ 4)
- ใช้ OAuth client แบบ Web ใน Google Cloud (Master ทำสำเร็จมาก่อน) | callback = `https://vdbmwmmsfrgpaauzspup.supabase.co/auth/v1/callback`
- ใส่ Client ID/Secret ที่ Supabase > Authentication > Google | Authorized JavaScript origins = โดเมนแอปจริง
- Redirect ใน PWA: ต้องทดสอบว่าเปิดจากไอคอน PWA แล้ววนกลับเข้าแอป ไม่หลุดไปแท็บเบราว์เซอร์ (ความเสี่ยงที่ยังไม่ตรวจ)
- รับเฉพาะ scope openid, email, profile

## 7. ปรับสัญญา Auth ของเดโมให้ตรงกับของจริง
เดโมกำหนด 7 เมธอด (session, signInGoogle, signInEmail, signUp, sendReset, signOut, deleteAccount) **ต้องเพิ่ม**: `verifyCode(email, code)`, `resendCode(email)`, `setNewPassword(code|session, pw)`, `linkGoogle()` (อนาคต) และเพิ่ม error code: `code_invalid`, `code_expired`, `too_many_requests`, `needs_link`, `unverified`
- เดโมใช้ httpOnly cookie ผ่าน Server ส่วนแอปจริงใช้ **Supabase session ฝั่ง client ที่ทำเสร็จแล้ว (v12 เดิม)** ต้องตัดสินใจว่าจะคงแบบเดิมหรือย้ายเป็น cookie -> คำถามเปิด (ดู §9)

## 8. ลบบัญชี (ปุ่มในหน้าตั้งค่าใหม่)
- ต้องลบ: ผู้ใช้ใน Supabase Auth + ข้อมูลทั้งหมดของผู้ใช้ (items, item_logs, chats, messages, notification_log, settings, push_subscriptions) ตาม `ON DELETE CASCADE`
- ลบ auth.users ต้องใช้ service key ฝั่ง Worker เท่านั้น (ห้ามให้ client เรียก) ยืนยันตัวตนซ้ำก่อนลบ (กรอกรหัส หรือยืนยัน Google ใหม่)
- ลบไม่ได้ย้อนกลับ | แสดงจำนวนรายการที่จะหายก่อนยืนยัน | แนะนำให้ดาวน์โหลดไฟล์สำรองก่อน

## 9. คำถามที่ยังเปิด (ต้องตัดสินก่อนลงมือ)
1. Session: คงแบบ Supabase ฝั่ง client (ที่ผ่านทดสอบแล้ว) หรือย้ายเป็น httpOnly cookie ตามเดโม? (ผมแนะนำคงเดิม เหตุผล: ผ่านทดสอบ 17/17 และ PWA ออฟไลน์พึ่ง token ฝั่งเครื่อง)
2. หน้ากรอกรหัส 6 หลัก/หน้าตั้งรหัสใหม่ ไม่มีในเดโม: ให้ผมออกแบบตามระบบดีไซน์เอง หรือ Master ทำเดโมเพิ่ม?
3. ลิงก์ในอีเมลบน Android มักเปิดเบราว์เซอร์ ไม่เปิด PWA: ยอมรับให้ลิงก์ยืนยันเสร็จที่เบราว์เซอร์แล้วค่อยกลับแอป หรือให้รหัส 6 หลักเป็นทางหลัก?

## 10. ลำดับเฟส (ยืนยันข้อ 5)
- เฟส A: นำ UI v12 ใส่ (MockAuth) | Gate: ภาพตรงเดโม 0 พิกเซล + ชุดทดสอบ route/ฟีเจอร์/ออฟไลน์ผ่าน + คง app-v11 เป็น rollback
- เฟส B: ต่อ Supabase Auth จริง + สวิตช์ + ชั้นป้องกัน §2 (ทดสอบ hook จริง) + Google
- เฟส C: นำเข้าข้อมูลเก่า (ทำแล้วในเฟส 1 ใช้ซ้ำได้)
- เฟส D (เมื่อมีโดเมน): Resend + เปิดสวิตช์ `true`
