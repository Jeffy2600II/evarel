# ระบบเลขรุ่น (Versioning) ของ Evarel

เอกสารฉบับทางการ กำหนดรูปแบบ ความหมาย และกติกาการขยับเลขรุ่นของแอป Evarel ใช้กับทุกสภาพแวดล้อม (forge และ production) เอกสารนี้ไม่ระบุเลขรุ่นปัจจุบัน เพราะเลขรุ่นปัจจุบันมีแหล่งความจริงเพียงแห่งเดียวคือ `releases/current.json`

## 1. ขอบเขตและวัตถุประสงค์

เลขรุ่นมีหน้าที่สามอย่าง
1. บอกผู้ใช้และผู้ดูแลว่าแอปที่กำลังใช้งานเป็นรุ่นใดและเก่าเพียงใด
2. บอกชนิดของการเปลี่ยนแปลง ว่าเป็นของใหม่ที่ผู้ใช้สัมผัสได้หรือเป็นการแก้ไขเท่านั้น
3. ใช้ยืนยันว่าระบบแจ้งอัปเดตทำงานถูกต้อง โดยเทียบเลขที่แอปรันอยู่กับเลขล่าสุดบนเซิร์ฟเวอร์

ระบบเลขรุ่นนี้ออกแบบสำหรับแอปที่ผู้ใช้ปลายทางใช้โดยตรงและปล่อยอัปเดตต่อเนื่อง ไม่ได้ออกแบบสำหรับไลบรารีที่มีผู้อื่นนำไปเรียกใช้ จึงไม่ใช้ Semantic Versioning ซึ่งเลขหลักตัวแรก (MAJOR) มีความหมายต่อเมื่อมี API ที่อาจทำให้ผู้เรียกใช้เสียหาย

## 2. รูปแบบ

```
<ปี>.<รอบ>.<แพตช์>[-<ช่อง>]
```

ตัวอย่าง: `2026.3.0`, `2026.3.2`, `2027.1.0`, `2026.3.2-forge`

| ส่วน | ชนิด | ความหมาย | ค่าที่ยอมรับ |
|---|---|---|---|
| ปี | จำนวนเต็ม 4 หลัก | ปี ค.ศ. ที่ปล่อยรุ่นนั้น | 2026 ขึ้นไป |
| รอบ | จำนวนเต็ม | ลำดับรอบการปล่อยของใหม่ภายในปี | 1 ขึ้นไป ไม่มีเลขศูนย์นำหน้า |
| แพตช์ | จำนวนเต็ม | ลำดับการแก้ไขภายในรอบ | 0 ขึ้นไป ไม่มีเลขศูนย์นำหน้า |
| ช่อง | ข้อความ | สภาพแวดล้อมที่ปล่อย | ดูข้อ 5 |

นิพจน์ตรวจรูปแบบ (ส่วนที่ไม่รวมช่อง): `^(\d{4})\.([1-9]\d*)\.(0|[1-9]\d*)$` กำหนดไว้ที่เดียวใน `scripts/version-rules.mjs`

## 3. ความหมายของการขยับเลข

| สิ่งที่เปลี่ยน | ขยับ | แพตช์ | ตัวอย่าง |
|---|---|---|---|
| ขึ้นปีปฏิทินใหม่ | ปี | รอบเป็น 1 แพตช์เป็น 0 | `2026.5.2` เป็น `2027.1.0` |
| ฟีเจอร์ใหม่หรือการเปลี่ยนที่ผู้ใช้สัมผัสได้ (โน้ตชนิด `new`) | รอบ | เป็น 0 | `2026.2.3` เป็น `2026.3.0` |
| ปรับปรุงหรือแก้ไขโดยไม่มีของใหม่ (โน้ตชนิด `improve` หรือ `fix` เท่านั้น) | แพตช์ | เพิ่ม 1 | `2026.3.0` เป็น `2026.3.1` |

หลักการตัดสิน
- การขยับต้องไม่น้อยกว่าที่ชนิดโน้ตกำหนด การขยับมากกว่าที่จำเป็นทำได้ เช่น การแก้ไขอย่างเดียวที่ขยับรอบ ถือว่าไม่ผิดกติกา
- เมื่อขยับรอบหรือปี ค่าที่อยู่ท้ายกว่าต้องรีเซ็ต ได้แก่ แพตช์เป็น 0 และเมื่อขึ้นปี รอบเป็น 1
- เลขรุ่นต้องเพิ่มขึ้นเสมอ ห้ามเท่าเดิมหรือย้อนกลับ
- ไม่มีการข้ามปีโดยไม่ขึ้นปี และปีต้องไม่ถอยหลัง

## 4. โน้ตรุ่น (Release Notes)

ทุกรุ่นที่ส่งถึงผู้ใช้ต้องมีโน้ตรุ่นเก็บใน `releases/current.json` โครงสร้าง

| ฟิลด์ | บังคับ | คำอธิบาย |
|---|---|---|
| `version` | ใช่ | เลขรุ่นตามข้อ 2 ไม่ใส่ช่อง |
| `date` | ใช่ | วันที่ปล่อย รูปแบบ `YYYY-MM-DD` |
| `title` | ไม่ | ชื่อรุ่นสั้นๆ |
| `notes` | ใช่ อย่างน้อย 1 ข้อ | รายการ `{ "type": "new" \| "improve" \| "fix", "text": "..." }` |

ชนิดโน้ตมีผลต่อการขยับเลขตามข้อ 3 จึงต้องเลือกชนิดตามความจริงของการเปลี่ยนแปลง ไม่ใช่เลือกให้เลขขยับตามที่ต้องการ

## 5. ช่อง (Channel)

ช่องระบุสภาพแวดล้อมที่รุ่นนั้นถูกปล่อย ระบบใส่ให้อัตโนมัติตอน build ผู้พัฒนาห้ามเขียนช่องลงใน `releases/current.json`

| สภาพแวดล้อม | ช่อง | เลขที่ผู้ใช้เห็น |
|---|---|---|
| production | ไม่มี | `2026.3.2` |
| forge | `forge` | `2026.3.2-forge` |

เลขฐาน (ไม่รวมช่อง) เป็นเลขเดียวกันในทุกสภาพแวดล้อมสำหรับรุ่นเดียวกัน ช่องมีไว้แยกว่ากำลังดูรุ่นที่ยังทดสอบอยู่หรือรุ่นที่ปล่อยจริง

## 6. รหัส build

นอกจากเลขรุ่น ทุก build มีรหัส build 12 ตัวอักษรฐานสิบหก คำนวณจากรายชื่อไฟล์ที่แคชร่วมกับเนื้อหา `releases/current.json` ดังนั้น เมื่อเนื้อโน้ตหรือเลขรุ่นเปลี่ยน รหัส build เปลี่ยนเสมอ ระบบแจ้งอัปเดตใช้รหัส build เป็นตัวเทียบว่ามีรุ่นใหม่หรือไม่ เลขรุ่นมีไว้ให้มนุษย์อ่าน รหัส build มีไว้ให้ระบบเทียบ

## 7. การแสดงผล

หน้าตั้งค่า หัวข้อ "เกี่ยวกับ" แสดงเลขรุ่น วันที่ และรหัส build ของแอปที่กำลังรันอยู่จริง ค่าเหล่านี้อ่านจาก service worker ที่ควบคุมหน้านั้นอยู่ ไม่ได้อ่านจากเซิร์ฟเวอร์ ด้วยเหตุผลต่อไปนี้ เมื่อมีอัปเดตค้างอยู่ รุ่นล่าสุดบนเซิร์ฟเวอร์ต่างจากรุ่นที่รันอยู่ การแสดงรุ่นล่าสุดจะทำให้เลขไม่ตรงความจริง และทำให้ตรวจการทำงานของหน้าต่างแจ้งอัปเดตไม่ได้

เลขรุ่นที่ service worker ตอบกลับมาเกิดจากค่า `APP_VERSION` ที่ฝังลงใน `sw.js` ตอน build ค่านี้ตรงกับ `version` ใน `release.json` ของ build เดียวกันเสมอ

## 8. กลไกบังคับ

| กลไก | ไฟล์ | สิ่งที่ตรวจ |
|---|---|---|
| กติกากลาง | `scripts/version-rules.mjs` | รูปแบบ เปรียบเทียบลำดับ และการขยับที่ถูกต้อง |
| ตัวตรวจในกระบวนการปล่อย | `scripts/check-release-notes.mjs` | เลขรุ่นถูกรูปแบบ ขยับถูกต้องเทียบกับ commit ฐาน และต้องมีโน้ตใหม่เมื่อมีไฟล์ที่ส่งถึงผู้ใช้เปลี่ยน |
| ตัว build | `scripts/build-next.mjs` | ปฏิเสธเลขรุ่นผิดรูปแบบ ใส่ช่อง ฝังเลขลง `sw.js` และสร้าง `release.json` |
| ชุดทดสอบกติกา | `tests/version_rules.test.mjs` | 19 กรณี ทั้งกรณีที่ต้องผ่านและต้องล้ม |
| ขั้นตอนอัตโนมัติ | `.github/workflows/web.yml` | รันตัวตรวจก่อน build และตรวจหลัง deploy ว่า `release.json` บนเว็บตรงกับที่เพิ่ง build |

ตัวตรวจเทียบกับประวัติ git จึงให้ผลเหมือนกันทั้งเครื่องผู้พัฒนาและบน GitHub Actions เมื่อล้ม กระบวนการปล่อยหยุดและไม่ deploy

## 9. ขั้นตอนปล่อยรุ่น

1. ตัดสินชนิดของการเปลี่ยนแปลง ว่ามีของใหม่ที่ผู้ใช้สัมผัสได้หรือไม่
2. แก้ `releases/current.json` ให้มีเลขรุ่นถัดไปตามข้อ 3 วันที่ และโน้ตตามจริง
3. รัน `node scripts/check-release-notes.mjs` ในเครื่อง ต้องได้ผลผ่าน
4. commit และ push ไปยังสาขา develop ขั้นตอนอัตโนมัติจะ build, deploy ไปยัง forge และตรวจผลหลัง deploy
5. ตรวจที่หน้าตั้งค่าว่าเลขรุ่นตรงกับที่ปล่อย

การปล่อยขึ้น production ใช้กติกาการขึ้นสาขา main ที่กำหนดไว้แยกต่างหาก

## 10. การเปลี่ยนผ่านจากระบบเลขเดิม

ก่อนใช้ระบบนี้ รุ่นทดลองใช้เลขรูปแบบ `0.x.y` ซึ่งเป็นเลขชั่วคราวสำหรับทดสอบระบบแจ้งอัปเดต ไม่ใช่รุ่นที่ปล่อยจริง ตัวตรวจยอมให้ข้ามจากเลขรูปแบบเดิมมาเป็นรูปแบบนี้ได้ครั้งเดียว หลังจากนั้นบังคับตามข้อ 3 ทุกครั้ง

## 11. ข้อจำกัด

- เลขรุ่นสะท้อนการเปลี่ยนที่ผู้ใช้สัมผัสได้ ไม่ได้สะท้อนขนาดของการแก้ไขโค้ดภายใน
- ตัวตรวจบังคับได้เฉพาะความสอดคล้องระหว่างชนิดโน้ตกับการขยับเลข ไม่สามารถตัดสินแทนมนุษย์ว่าการเปลี่ยนแปลงหนึ่งๆ ควรจัดเป็น `new` หรือ `fix` การจัดชนิดที่ไม่ตรงความจริงเป็นความรับผิดชอบของผู้ปล่อยรุ่น
- เมื่อแก้ไขเฉพาะไฟล์ที่ไม่ส่งถึงผู้ใช้ (เอกสาร ชุดทดสอบ) ไม่จำเป็นต้องขยับเลขรุ่น
