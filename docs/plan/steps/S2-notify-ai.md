# S2 แจ้งเตือนและ AI (ช่วง: ใกล้ ละเอียดเต็ม)

กลับไปที่ [แผนหลัก](../MASTER-PLAN.md) | ขั้นก่อนหน้า [S1](S1-accounts-email.md) | ขั้นถัดไป [S3](S3-nextjs-wrap.md)

## เป้าหมาย
1. ผู้ใช้ได้รับการแจ้งเตือนถึงเครื่องจริงตามเวลาที่ตั้งไว้ในแต่ละงานหรือกิจวัตร ตลอดเวลาที่มีรายการที่ตั้งแจ้งเตือน (ปรับแก้จากเดิมที่เป็นสรุปตอนเช้าวันละครั้ง ตามที่ Master สั่ง 13 ต.ค. 2026)
2. AI ใช้งานจริงบน Android สั่งงานด้วยภาษาไทยได้ภายในโควตาต่อผู้ใช้

## ผลลัพธ์ที่ตรวจได้ (เกณฑ์สำเร็จของขั้นนี้)
1. ตั้งเตือนในรายการหนึ่งรายการ ปิดแอป แล้วการแจ้งเตือนถึงเครื่องจริงตรงเวลา (วัดความคลาดเคลื่อนเป็นนาที)
2. รายการที่ถูกลบหรือแก้เวลาแล้วไม่แจ้งเตือนด้วยเวลาเก่า
3. แจ้งเตือนซ้ำไม่เกิดสำหรับรายการเดียวกันในเวลาเดียวกัน
4. ผู้ใช้ที่ปิดสิทธิ์แจ้งเตือนไม่ถูกส่ง และรายการสมัครรับที่หมดอายุถูกล้าง
5. ตัวจัดเวลาทำงานภายในเพดานเวลา CPU ของแผนฟรี (ดู [platform-limits.md](platform-limits.md)) โดยวัดจริง
6. AI สั่งเพิ่มและแก้งานด้วยภาษาไทยได้บน Android จริง และเมื่อใช้ครบโควตาได้ข้อความที่อ่านเข้าใจ

## สถานะจริง ณ 15 ต.ค. 2026 (แทนที่ส่วน "ข้อเท็จจริงที่ตรวจแล้ว" และ "แนวทางที่เลือก" ด้านล่างที่เขียนก่อนลงมือ)

ส่วนที่เขียนไว้ก่อนลงมือด้านล่างถูกเก็บไว้เป็นหลักฐานการวัด แต่ข้อความที่ระบุว่า "ไม่มีตัวจัดเวลาในซอร์สหลัก" และ "ตัวจัดเวลารันบน Cloudflare Cron" **ล้าสมัยแล้ว**

- **ตัวส่งแจ้งเตือนจริงอยู่ที่ Supabase:** pg_cron (ทุกนาที) เรียก Edge Function `notify-tick` ผ่าน pg_net ค่า URL และความลับเก็บใน Vault Cloudflare cron ของชุด forge ปิดแล้ว (`crons = []`) ส่วน production (`evarel-api`) ไม่เคยมี cron
- **เหตุผลที่ย้าย:** ผลวัดด้านล่างชี้ว่า Cloudflare ส่งได้ไม่เกิน 2 ข้อความต่อรอบเพื่อรักษาเพดาน CPU 10 ms ซึ่งเป็นเพดานต่ำ Master ตัดสินใจย้ายเพื่อโควตาที่ยืดหยุ่นกว่า [Edge Function ของ Supabase ยังไม่ได้วัดเพดานการส่งต่อรอบ จึงห้ามอ้างว่าส่งได้มากกว่า 2 จนกว่าจะวัด]
- **คีย์ VAPID:** สร้างชุดใหม่ชุดเดียวใช้ทั้ง Supabase และ Worker แอปถามคีย์สาธารณะจาก Worker (`/push/key`) ทุกครั้ง ถ้าสองฝั่งคนละชุด Push ล้มเงียบ จึงห้ามเปลี่ยนคีย์ฝั่งเดียว
- **ผลทดสอบบนเครื่องจริง (Master ทดสอบเอง 15 ต.ค. 2026):** Push จาก Supabase เด้งถึงมือถือ Android, แก้เวลาแล้วเด้งตามเวลาใหม่, ตั้งเวลาที่ผ่านไปแล้วไม่เด้งย้อน, เลื่อนเวลา "นอนก่อน" มาทดสอบแล้วเด้งปกติ
- **โค้ด:** อยู่บนสาขา develop (commit 41e4023) ยังไม่ merge เข้า main ตามกฎ
- **ที่ยังไม่ได้ทำ:** ตัวส่งสำหรับ production (`evarel-api`) เพราะทุกอย่างทดสอบบนชุด forge ต้องตัดสินใจในขั้น S5 ยังไม่ได้วัดเพดานจำนวนข้อความต่อรอบของ Supabase และยังไม่ได้รันประตู 3 ชุดปิดขั้นนี้หลังย้ายตัวส่งใหม่

**สถานะขั้น S2:** ใกล้ปิด เหลือรันประตู 3 ชุด (ภาพ 0 พิกเซล, route 22 / feature 13, ออฟไลน์) หลังการเปลี่ยนล่าสุด

## ข้อเท็จจริงที่ตรวจแล้ว (13 ต.ค. 2026)
- โมเดลข้อมูลมีฟิลด์เตือนต่อรายการอยู่แล้ว (รายการเตือนแบบก่อนเวลา กี่นาที) ที่ขาดคือตัวตรวจและส่งตามเวลา
- ฝั่งแอป: service worker แสดงการแจ้งเตือนได้ และหน้าตั้งค่าขอสิทธิ์ได้แล้ว
- ฝั่ง Worker หลัก (src/): มีเฉพาะเส้นทาง AI สามเส้นทาง (โควตา แชต ความจำ) ไม่มีเส้นทาง Push และไม่มีตัวจัดเวลา (scheduled) เลย
- ต้นแบบ evarel-poc ส่ง Push ถึง Android จริงได้แล้วเมื่อ 9 ต.ค. 2026 มีเส้นทางสำหรับคีย์ สมัครรับ และส่ง แต่ไม่มีตัวจัดเวลา และไม่ใช่โค้ดในซอร์สหลัก
- AI: เครื่องยนต์ แชต ความจำ และโควตาต่อผู้ใช้อยู่ในซอร์สหลักแล้ว ทดสอบบนระบบจริงผ่านเมื่อ 11 ต.ค. 2026 (ตัวเลขโควตา 30 ครั้งต่อนาที และ 40 ครั้งต่อวันต่อผู้ใช้)

## ข้อมูลจริงจากการสำรวจ (13 ต.ค. 2026)
- Cron Trigger ที่บัญชีใช้แล้ว: 0 จาก 5 (อ่านจาก API ของ 5 Worker ในบัญชี) ที่เหลือใช้ร่วมกันทุก Worker
- ต้นแบบ evarel-poc ใช้ webpush-webcrypto 1.0.5 (WebCrypto ล้วน) มีเส้นทางคีย์ สมัครรับ ส่ง ไม่มี scheduled อ่านจากสำเนาโค้ดที่บันทึก 12 ต.ค. ไม่ได้อ่านจากตัวที่รันอยู่ เพราะ API อ่านโค้ดคืนเวอร์ชันที่อัปโหลดล่าสุดแทนเวอร์ชันที่ใช้งาน
- ต้นทุนเข้ารหัส Push หนึ่งข้อความ 2.0 ถึง 2.75 มิลลิวินาที วัดบน Node ด้วยไลบรารีตัวเดียวกันและ subscription ปลอม ไม่ใช่ตัวเลขของ Cloudflare ต้องวัดซ้ำบน Workers จริง
- CPU จริงของ Worker หลักในช่วง 3 ชั่วโมงที่ผ่านมา 45 คำขอ: P50 4.56 มิลลิวินาที P99 14.08 มิลลิวินาที ไม่มีข้อผิดพลาด เอกสารทางการระบุว่ามีความยืดหยุ่นเมื่อเกินเพดานเป็นครั้งคราว แต่ถ้าเกินสม่ำเสมอจะถูกตัด

## แนวทางที่เลือก (รอวัดซ้ำบน Workers จริงก่อนเปิดใช้กับผู้ใช้จริง)
ตัวจัดเวลาหนึ่งตัวรันทุกนาที ค้นเฉพาะรายการที่ถึงเวลา ส่งไม่เกิน 3 รายการต่อรอบ บันทึกว่าแจ้งแล้วทันที ที่เหลือค้างรอรอบถัดไป ไม่เลือก Durable Objects หรือ Queues เพราะเกินงบศูนย์บาทและซับซ้อนเกินจำเป็น ไม่ส่งทั้งหมดในรอบเดียวเพราะเกินเพดานเมื่อหลายคนตั้งเวลาเดียวกัน

## ข้อกำหนดความปลอดภัยของตัวจัดเวลา (ผล STRIDE 13 ต.ค. 2026 ก่อนเขียนโค้ด)
ตัวจัดเวลาใช้ service key ซึ่งข้ามการจำกัดสิทธิ์ระดับแถว ทุกข้อด้านล่างจึงเป็นเงื่อนไขของขั้นพัฒนา ไม่ใช่ข้อเสนอ

| ภัย | ข้อกำหนด |
|---|---|
| ปลอมตัว | ผูก subscription กับ user_id ที่ตรวจจาก JWT เท่านั้น ไม่รับ user_id จากเนื้อหาคำขอ และจำกัด endpoint ให้อยู่ในโดเมนของบริการ Push ที่รู้จัก |
| แก้ข้อมูล | ตัวจัดเวลาอ่านรายการของเจ้าของ subscription เดียวกันเท่านั้น |
| ปฏิเสธการกระทำ | บันทึกการส่งทุกครั้งพร้อมเวลาและผล ใช้กันแจ้งซ้ำด้วย |
| เปิดเผยข้อมูล | ไม่ใส่ข้อมูลอ่อนไหวใน payload และให้ผู้ใช้ปิดการแสดงชื่องานบนหน้าจอล็อกได้ |
| ถล่มระบบ | ส่งไม่เกิน 3 รายการต่อรอบ และมีเพดานจำนวนรายการเตือนต่อผู้ใช้ ต้องตรวจว่าเพดานข้อมูลเดิมครอบคลุมฟิลด์เตือน |
| ยกระดับสิทธิ์ | ทุกคำค้นมีเงื่อนไข user_id ชัดเจน และมีเทสต์พิสูจน์ว่าข้อมูลไม่ข้ามผู้ใช้ เหมือนที่ทำกับโควตา AI |

## ผลวัดบน Cloudflare Workers จริง (13 ต.ค. 2026)
วัดด้วยเวอร์ชันพรีวิวของ evarel-poc ที่ไม่รับทราฟฟิกใช้งานจริง เข้ารหัสข้อความ Push ด้วยไลบรารีตัวเดียวกับต้นแบบ ใช้ subscription ปลอม ไม่ยิงเครือข่าย อ่านค่า CPU จากเมตริกของ Cloudflare เพราะนาฬิกาในโค้ดบน Workers หยุดนิ่ง ระดับละ 7 ถึง 8 คำขอ

| ส่งกี่ข้อความต่อคำขอ | CPU น้อยสุด | ค่ามัธยฐาน | มากสุด |
|---|---|---|---|
| 0 (Worker เปล่า) | 0.33 ms | 0.45 ms | 0.71 ms |
| 1 | 1.35 ms | 1.65 ms | 2.74 ms |
| 3 | 1.77 ms | 2.70 ms | 4.22 ms |
| 5 | 2.21 ms | 2.90 ms | 3.82 ms |

- ต้นทุนประมาณ 0.87 + 0.47 คูณจำนวนข้อความ มิลลิวินาที ข้อความแรกแพงสุด ข้อความถัดไปราว 0.5 มิลลิวินาที ต่ำกว่าที่วัดบน Node (2.0 ถึง 2.75) มาก
- ความแกว่งภายในระดับเดียวกัน (1.4 ถึง 2 มิลลิวินาที) มากกว่าความต่างระหว่างระดับ จึงอ่านเส้นถดถอยเป็นตัวเลขแม่นยำไม่ได้
- ยังไม่ได้วัด: อ่านฐานข้อมูล แยกวิเคราะห์ JSON ยิงไปบริการ Push จริง และอัปเดตสถานะส่งแล้ว ซึ่งต้องวัดในตัวจัดเวลาจริง
- CPU ของ Worker หลักย้อนหลัง 24 ชั่วโมง (118 คำขอ) ไม่มีข้อผิดพลาดเลย มัธยฐาน 3.8 ms เกิน 10 ms จำนวน 6 จาก 75 คำขอเดี่ยว (สูงสุด 21.5 ms) ทั้งหมดสำเร็จ ไม่ถูกตัด เอกสารทางการระบุว่าเกินเป็นครั้งคราวได้ แต่เกินสม่ำเสมอจะถูกตัด ยังไม่ทราบว่าสม่ำเสมอคือเท่าไร จึงต้องเฝ้าดูเมื่อผู้ใช้เพิ่ม

## งานย่อยตามลำดับ
1. วัดก่อนออกแบบ: ตัวจัดเวลาที่ตรวจรายการถึงกำหนดควรอ่านฐานข้อมูลอย่างไรจึงอยู่ในเพดาน CPU 10 มิลลิวินาที และ subrequest 50 ต่อครั้ง
2. ย้ายความสามารถ Push (คีย์ สมัครรับ ส่ง) จากต้นแบบเข้าซอร์สหลัก ให้ผูกกับผู้ใช้ที่ล็อกอิน
3. สร้างตัวจัดเวลาแบบรันทุกนาทีหนึ่งตัว และบันทึกว่ารายการใดแจ้งไปแล้ว เพื่อไม่ซ้ำ
4. ทดสอบกับเครื่อง Android จริง วัดความคลาดเคลื่อนของเวลา
5. ตรวจ AI บน Android จริงตามเกณฑ์ข้อ 6

## ความเสี่ยงและช่องว่างที่ยังเปิด
- ตัวจัดเวลาทุกนาทีใช้ Cron Trigger หนึ่งในห้าตัวของทั้งบัญชี และทุก Worker ในบัญชีใช้โควตาร่วมกัน
- เพดาน 10 มิลลิวินาทีนับเฉพาะเวลา CPU ไม่นับเวลารอเครือข่ายหรือรอฐานข้อมูล (ตรวจจากเอกสารทางการ 13 ต.ค. 2026) ส่วนที่กิน CPU จริงคือการแปลงข้อมูลและเข้ารหัสข้อความ Push ยังไม่ทราบว่ารวมแล้วเกิน 10 มิลลิวินาทีหรือไม่ ต้องวัดจริงตามข้อ 1 ของงานย่อย ถ้าเกินต้องแบ่งงานหรือเปลี่ยนวิธี
- จำนวนคำขอ 100,000 ต่อวันของ Cloudflare: ตัวจัดเวลาทุกนาทีกินประมาณ 1,440 ครั้งต่อวัน ยังไม่รวมการสมัครรับและส่ง
- OpenRouter สำรองยังไม่ได้ตรวจโควตา
- การแจ้งเตือนแบบสรุปตอนเช้าที่ Master เคยเลือกเพื่อประหยัดโควตา AI ถูกแทนที่ด้วยการแจ้งเตือนตามเวลาที่ตั้ง หากอยากได้สรุปตอนเช้าเพิ่มเป็นฟีเจอร์เสริม ให้ Master ตัดสินแยก

## ขอบเขตที่ไม่ทำในขั้นนี้
สรุปอัจฉริยะด้วย AI ตอนเช้าและสรุปสิ้นวัน (เลื่อนไปหลังหมุดหมาย) การแจ้งเตือนตามตารางเรียน (ผู้ใช้ตั้งเองได้ผ่านรายการ)

## การตัดสินใจเพดานต่อรอบ
ตัวจัดเวลาส่งไม่เกิน 5 รายการต่อรอบ (ปรับจาก 3 ตามผลวัดบน Workers จริง) ส่วนที่ไม่ได้วัดยังเหลือเผื่อประมาณ 6 มิลลิวินาที ไม่ไปไกลกว่า 5 เพราะข้อมูลยังไม่พอ ต้องวัดซ้ำในตัวจัดเวลาจริงก่อนปรับเพิ่ม
