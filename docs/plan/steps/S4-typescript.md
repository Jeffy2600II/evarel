เพิ่มเข้าแผน 16 ต.ค. 2026 ตามคำสั่ง Master: ขั้นนี้ไม่เคยอยู่ใน S3 (S3 คือการครอบด้วย Next.js โดยไม่แตะโค้ดแอป) เลขขั้นถัดไปถูกขยับแล้ว S4 เดิมเป็น S5 S5 เดิมเป็น S6 S6 เดิมเป็น S7

## เป้าหมาย
เมื่อจบขั้นนี้ ระบบส่วนหน้าทำงานบน Next.js เต็มรูปแบบ (หน้าเป็นส่วนประกอบของ Next เอง ไม่ใช่ HTML เดิมที่ปล่อยผ่านเหมือน S3) เขียนด้วย TypeScript และ React โดยผู้ใช้เห็นและใช้งานทุกอย่างเหมือนเดิมเป๊ะ ไม่รู้เลยว่าเบื้องหลังเปลี่ยนเฟรมเวิร์กกับภาษา รวมถึงฝั่ง host (Cloudflare) ที่ต้องตั้งค่าให้รองรับขั้นคอมไพล์

หลักการที่ Master กำหนด: แปลงด้วยการคำนวณและพิสูจน์ความเท่าเดิมของพฤติกรรม ไม่ใช้เครื่องมือแปลงอัตโนมัติแบบธรรมดา เพราะจะทิ้งงานแก้ตามมามาก

ขอบเขตหลังปรับ (16 ต.ค. 2026 ตามคำสั่ง Master): งานแปลงเป็น React ย้ายมารวมในขั้นนี้จาก S5 เดิม ส่วน S5 เหลือเฉพาะการเปลี่ยนเป็น Tailwind ดู [S5](S5-react-pages.md)

## ผลลัพธ์ที่ตรวจได้ (ร่าง ต้องยืนยันกับ Master ก่อนลงมือ)
1. ประตู 3 ชุดผ่านครบหลังแปลงแต่ละโมดูล: ภาพ 0 พิกเซล, route 22 กับ feature 13, ออฟไลน์
2. ผลลัพธ์ของฟังก์ชันคำนวณ (วันที่ ตารางซ้ำ สถิติ) ระหว่างฉบับ JS กับฉบับ TS เท่ากันทุกกรณีทดสอบด้วยอินพุตชุดเดียวกัน
3. ลำดับการโหลดโมดูลและรายการแคชของ service worker ตรงกันกับก่อนแปลง (ประตูลำดับเดิม)
4. เครื่องที่มีแคชรุ่นเก่าอัปเดตได้โดยไม่เห็นหน้าเก่าค้าง (ใช้ชุดทดสอบอัปเดต service worker ที่มีอยู่)
5. ตัวตรวจชนิดข้อมูลของ TypeScript ไม่มี error
6. ผลส่งออกของ build ไม่ได้ปล่อยไฟล์แอปเดิมผ่านตรงๆ อีกต่อไป หน้าถูกสร้างจากส่วนประกอบ React ของ Next เอง และไม่มีไฟล์ JavaScript ต้นฉบับของแอปเหลือในเส้นทางที่เสิร์ฟ
7. หน้าที่ยังไม่แปลงทำงานได้ตามเดิมตลอดช่วงแปลง หน้าที่แปลงแล้วผ่านประตู 3 ชุดก่อนเริ่มหน้าถัดไป ไม่ผ่านต้องย้อนกลับหน้านั้น
8. ไม่ขึ้น production จนกว่า Master สั่ง

## ข้อเท็จจริงที่วัดแล้ว (16 ต.ค. 2026 วัดจากโค้ดจริง)
- ส่วนหน้ามีโมดูล 26 ไฟล์ รวม 988 บรรทัด ใหญ่สุด 125 บรรทัด (25-actions.js) เล็กสุด 9 บรรทัด และยังเป็น JavaScript ทั้งหมด ไม่มีไฟล์ .ts
- โฟลเดอร์ app-ts ถึง app-ts10s1 รวม 15 โฟลเดอร์ ภายในเป็น JavaScript ล้วน ไม่มี TypeScript (ของทดลองรอบก่อน ยังไม่ได้ใช้)
- โมดูลไม่ได้ใช้ import/export จริง แม้โหลดด้วย script type=module แต่แชร์กันผ่าน Object.assign(window, ...) กับตัวแปรกลาง ST ผลคือ TypeScript มองไม่เห็นว่าใครใช้สัญลักษณ์ใดจากไหน ต้องประกาศชนิดของ window และ ST ส่วนกลางก่อนแปลงโมดูลใด
- มีตัวตรวจ dependency อยู่แล้ว (tools/dep_symbols.mjs, tools/dep_manifest.mjs) และประตูลำดับโมดูล ใช้เป็นเครื่องกันพลาดได้
- ส่วนหลังบ้าน (app/api/src) เป็น TypeScript อยู่แล้ว 20 ไฟล์ ไม่อยู่ในขอบเขตขั้นนี้

## การตัดสินใจลำดับ (16 ต.ค. 2026 Master มอบให้ผู้พัฒนาเลือกทางที่เหมาะที่สุด)
เลือก: ทำ TypeScript ก่อน React (S5) และคงรูปแบบ window กับ ST เดิม ไม่ย้ายไป import/export ในขั้นนี้

เหตุผลจากข้อมูลที่วัด:
- ST ถูกอ้าง 309 ครั้งจากเพียง 16 ฟิลด์ ประกาศชนิดครั้งเดียวคลุมทั้งหมด
- สัญลักษณ์ที่ส่งออกผ่าน window มี 320 ตัว และโมดูลใช้ข้ามไฟล์ 437 จุด ถ้าย้ายไป import/export พร้อมกันต้องแตะ 437 จุดนี้และกระทบลำดับโหลดกับรายการแคชของ service worker ซึ่งเป็นความเสี่ยงที่ผู้ใช้เห็นผลโดยตรง ขัดเป้าหมายที่ผู้ใช้ต้องไม่รู้สึกต่าง
- ทำ React ก่อนจะเขียนบนฐานที่ไม่มีชนิดข้อมูล บั๊กจากชื่อฟิลด์ผิดจะปนกับบั๊กจากการแปลงหน้า แยกสาเหตุยาก ส่วน TypeScript ก่อนให้ตาข่ายนิรภัยตอนทำ React ทีละหน้า
- ไม่มี inline handler ในสตริง HTML (วัด 0 จุด) จึงไม่มีโค้ดซ่อนที่ตัวตรวจชนิดมองไม่เห็น

## ผลตรวจชนิดข้อมูลบนโค้ดเดิม (วัดจริง 16 ต.ค. 2026 บนสำเนา ไม่แตะไฟล์จริง)
ตัวตรวจ tsc 7.0.2 เปิด checkJs โหมดหลวมสุด ไม่แก้โค้ดสักบรรทัด ได้ 99 จุด ตรวจมือครบทุกกลุ่ม:
- 75 จุด: ไม่รู้ชนิดของ e.target และ element ต้องใส่ type cast ไม่ใช่บั๊ก
- 11 จุด: เดาชนิดผิดจากพารามิเตอร์ default ว่าง ไม่ใช่บั๊ก
- 4 จุด: ลบ Date สองตัวในตรรกะตารางซ้ำ ถูกต้องใน JavaScript แต่ TypeScript ไม่ยอมลบ Date ตรงๆ ไม่ใช่บั๊ก
- 2 จุด: FullCalendar ไม่มีไฟล์ชนิดข้อมูล (ไลบรารีภายนอก)
- 7 จุด: อื่นๆ ตรวจมือแล้วเป็นการใช้งานถูกต้องใน JavaScript
- บั๊กจริงที่พบ: 0 จุด
ข้อสรุป: โค้ดเดิมไม่มีบั๊กชนิดข้อมูลให้ซ่อม คุณค่าของขั้นนี้คือกันบั๊กในอนาคตตอนแก้ไขและตอนทำ React ไม่ใช่แก้ของเดิม ไฟล์ที่มีจุดมากสุดคือ 25-actions.js (40) และ 22-views__auth.js (15)

## ลำดับลงมือ (เรียงจากเสี่ยงต่ำไปสูง ทุกชั้นต้องผ่านประตู 3 ชุดก่อนไปชั้นถัดไป)
1. ชั้น 1 ตัวตรวจอย่างเดียว: เพิ่ม tsconfig แบบ checkJs และประกาศชนิดของ ST กับ window ในไฟล์ .d.ts ไฟล์เดียว ไม่แก้โมดูลใดและไฟล์ที่ส่งให้ผู้ใช้เหมือนเดิมทุกไบต์ (พิสูจน์ได้ด้วย hash)
2. ชั้น 2 ใส่ชนิดผ่านคอมเมนต์ JSDoc ทีละโมดูลตามกราฟ dependency ยังเป็นไฟล์ .js เดิม ไม่ต้องมีขั้นคอมไพล์ และไม่กระทบ service worker
3. ชั้น 3 เปลี่ยนนามสกุลเป็น .ts พร้อมขั้น build (เดิมระบุว่าตัดสินภายหลัง แต่เป้าหมายใหม่ต้องใช้ Next.js เต็มรูปแบบ ซึ่งคอมไพล์ TypeScript ให้อยู่แล้ว จึงมีแนวโน้มต้องทำ) ชั้นนี้เป็นชั้นแรกที่แตะ service worker และการ build บน Cloudflare
4. ชั้น 4 ย้ายจากการปล่อยไฟล์แอปเดิมผ่านตรงๆ ไปสร้างหน้าด้วยส่วนประกอบ React ของ Next ทีละส่วน โดยหน้าที่ยังไม่ย้ายยังเสิร์ฟจากของเดิม ต้องออกแบบกลไกให้ของเดิมกับของใหม่อยู่ร่วมกันได้ (ยังไม่ได้ออกแบบ)
5. ชั้น 5 เมื่อย้ายครบ เอาเส้นทางปล่อยผ่านออก ลบความจำเป็นต้องมี window กับ ST แบบเดิม และตรวจว่าไม่มีไฟล์ต้นฉบับเหลือในเส้นทางที่เสิร์ฟ

## สถานะ (16 ต.ค. 2026)
ชั้น 1 เสร็จ: ตัวตรวจชนิดแบบอ่านอย่างเดียว (tools/typecheck.mjs) กับไฟล์ชนิดของ ST (types/st.d.ts) ผูกกับ ST ด้วย JSDoc หนึ่งบรรทัดใน 00-head.js ผลวัด: 99 จุดเท่า baseline ทั้งชุดและไม่มีบั๊กจริง ตัวตรวจจับการพิมพ์ชื่อฟิลด์ ST ผิดได้ เทสต์ 4/4 ประตูผ่านครบบน build ใหม่ (ภาพ 20, route 22, feature 13, ออฟไลน์ 8, ลำดับ, console, อัปเดต v48 เป็น v49 8/8) ไฟล์ที่ส่งผู้ใช้เปลี่ยนสองไฟล์คือ 00-head.js (คอมเมนต์หนึ่งบรรทัด) กับ sw.js (VERSION เป็น evarel-v49-types) ข้อค้นพบ: การผูกชนิดไม่ลด 99 จุดเดิม คุณค่าคือกันพิมพ์ผิดในอนาคตเท่านั้น

ชั้น 2 เสร็จรอบแรก (16 ต.ค. 2026): ลด 99 เหลือ 26 จุดโดยไม่แตะไฟล์ที่ส่งผู้ใช้เลย ด้วยไฟล์ชนิดสองชุดนอกโฟลเดอร์ที่เสิร์ฟ (types/dom.d.ts ขยายชนิด DOM ให้ตรงที่โค้ดใช้จริง, types/globals.d.ts ประกาศ EVAREL_API กับ FullCalendar) baseline เป็น 26 เทสต์ 6/6 รวม T5 กับ T6 ที่พิสูจน์ว่าสะกดเมธอด DOM ผิดยังถูกจับ ข้อควรรู้: ทดลองใส่ JSDoc ที่ตัวโค้ด 3 จุดแล้วเกิด error ใหม่ (closest คืน Element) จึงเลือกทางไฟล์ชนิดแทน ข้อจำกัดที่รู้: dom.d.ts ทำให้ตัวตรวจไม่เตือนกรณี target เป็น document หรือ window ที่ไม่มี closest (โค้ดจริงกันด้วย ?. ที่ keydown, pointerout, contextmenu)

26 จุดที่เหลือ: 11 จุดมาจาก raw ใน 05-data__auth.js ที่ TS อนุมานตัวเลือกเป็น {method?} ต้องแตะ 1 บรรทัด (JSDoc ของ raw) 7 จุด trim บน FormData 4 จุดลบวันที่สองค่า (ถูกต้องใน JS ไม่แตะลอจิกตารางเวลา) ที่เหลือเป็นของเดี่ยว ชั้นถัดไป: JSDoc ของ raw (ไฟล์ผู้ใช้ 1 ไฟล์ ต้อง bump แคชและรันประตูทั้งชุด)

## ข้อเท็จจริงเพิ่มเติมสำหรับส่วน React (วัดจากโค้ดจริง 16 ต.ค. 2026)
- มี 6 route: วันนี้ รายการ ปฏิทิน สถิติ (แท็บ) และ ผู้ช่วย AI กับ ตั้งค่า (หน้าเต็ม) อยู่ใน route.js
- แอปทั้งหมดอยู่ในองค์ประกอบ id=page ตัวเดียว หน้าจอถูกสร้างจากสตริง template HTML ราว 90 จุดใน 10 ไฟล์ ไม่ใช่ไฟล์หน้าแยกกัน
- ผลคือ แปลงเป็น React ทีละหน้า ไม่ตรงกับโครงจริงตรงๆ เพราะไม่มีหน้าที่แยกเป็นไฟล์ให้ย้ายทีละไฟล์ ต้องกำหนดหน่วยการแปลงใหม่ (เช่นทีละ route หรือทีละส่วนประกอบ) ยังไม่ได้ตัดสิน

## สิ่งที่ยังไม่ทราบ
- หน่วยการแปลงเป็น React ที่เหมาะ (ทีละ route ทีละส่วนประกอบ หรืออย่างอื่น) และกลไกให้ของเดิมกับของใหม่อยู่ร่วมกันระหว่างแปลง รวมถึงผลต่อ service worker และรายการแคช
- Next.js แบบ static export รองรับครบตามที่แอปต้องการไหม (เช่น ทำงานออฟไลน์ แคชปฏิทิน การลงทะเบียน service worker) ยังไม่ได้พิสูจน์ในแบบที่หน้าถูกสร้างโดย Next เอง S3 พิสูจน์แค่แบบปล่อยผ่าน
- ขั้นนี้เป็นขั้นที่หนักที่สุดของแผน เพราะเปลี่ยนโครงทั้งระบบ จึงยังไม่ได้ตัดสินว่าควรจัดเป็นขั้นที่เลื่อนได้หรือไม่ การเลื่อนเป็นของ Master
- เวลาที่ใช้จริง ยังไม่เคยวัด

## รายละเอียดเมื่อใกล้ถึง
ขยายเป็นงานย่อยและเกณฑ์รายโมดูลเมื่อ Master ยืนยันขอบเขตและวิธีคอมไพล์ ลำดับแปลงเรียงจากโมดูลที่ไม่พึ่งใครตามกราฟ dependency
