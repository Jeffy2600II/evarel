# S1 บัญชีและอีเมล (ช่วง: ผ่านแล้ว ปิดเมื่อ 13 ต.ค. 2026)

กลับไปที่ [แผนหลัก](../MASTER-PLAN.md) | ขั้นถัดไป [S2](S2-notify-ai.md)

## เป้าหมาย
ผู้ใช้สมัคร ยืนยันอีเมล และกู้รหัสผ่านด้วยรหัส 6 หลักที่ระบบ Evarel ออกและส่งเอง ไม่พึ่งอีเมลในตัวของ Supabase เพราะ Supabase ไม่อนุญาต SMTP ส่วนตัวอย่าง Gmail

## ผลลัพธ์ที่ตรวจได้ (เกณฑ์สำเร็จของขั้นนี้)
1. สมัครแล้วรหัสถึงกล่องอีเมลจริง ใส่รหัสแล้วเข้าแอปได้
2. ลืมรหัสผ่านแล้วขอรหัส ยืนยัน ตั้งรหัสใหม่ และล็อกอินด้วยรหัสใหม่ได้ครบวงจรบนระบบจริง
3. รหัสผิดครบ 5 ครั้งแล้วรหัสถูกล็อก แม้ครั้งที่หกใส่รหัสถูกก็ไม่ผ่าน
4. อีเมลที่ไม่มีบัญชีและอีเมลที่มีบัญชีได้คำตอบเหมือนกันทั้งเนื้อหา สถานะ และเวลา
5. ไม่พบรหัสผ่านหรือโทเคนในไฟล์ใดของที่เก็บ
6. ชุดทดสอบเดิมของ Worker ไม่ถดถอย

## ข้อเท็จจริงที่ตรวจแล้ว (12 ถึง 13 ต.ค. 2026)
- Worker ส่งอีเมลผ่าน smtp.gmail.com พอร์ต 465 ได้จริง ใช้ CPU 0.69 มิลลิวินาทีต่อคำขอ (ตัวอย่างเดียว ต้องวัดซ้ำตอนใช้งานจริง)
- Supabase ออกเซสชันฝั่งเซิร์ฟเวอร์ได้โดยไม่ส่งอีเมลของตัวเอง ใช้ซ้ำไม่ได้ พิสูจน์บนระบบจริงแล้ว
- ตารางรหัสและฟังก์ชันตรวจรหัสแบบอะตอมิกลงบน Supabase จริงแล้ว (migration 004) ทดสอบบนระบบจริงผ่าน 7 ข้อ
- รหัสเดินทางถึงกล่องอีเมลของ Master จริงเมื่อ 13 ต.ค. 2026 (ฝั่งส่งผ่านแล้ว ฝั่ง verify ด้วยรหัสจริงยังไม่ได้ทดสอบ)
- โค้ดรวมเข้า main แล้ว (a615a4b) และ push ขึ้น GitHub แล้ว Worker evarel-api-b-test (0de4a2e1) เหมือนกับ build จาก main ทุกตัวอักษร
- ชุดทดสอบ 225 ข้อผ่านหมดบน main
- verify บนระบบจริงด้วยบัญชีทดสอบของเอเจนต์ผ่าน 13 ข้อ รวมตั้งสถานะยืนยันอีเมล (PUT admin) ที่เคยไม่เคยทดสอบกับของจริง บัญชีทดสอบถูกลบ ตกค้าง 0
- เพดานส่งอีเมลรวม 24 ชั่วโมง ค่าเริ่มต้น 400 ปรับด้วย MAIL_DAILY_CAP ล้มแบบปิดเมื่อนับไม่ได้
- วัดเวลาตอบลืมรหัสผ่านบนระบบจริง เส้นทางตอบ sent ล้วน 3 ตัวอย่างต่อฝั่ง: เนื้อหาและสถานะเหมือนกัน เวลา median ต่างกัน 55 ms ในช่วงแกว่งของเครือข่าย ตัวอย่างน้อย สรุปว่าไม่พบความต่างที่แยกจากสัญญาณรบกวนได้ แต่ยืนยันว่าไม่มีความต่างเลยไม่ได้

## งานย่อยตามลำดับ
1. ตรวจ verify ด้วยรหัสจริงบนระบบจริง: ทำแล้ว
2. ปิดช่องว่างที่ตรวจพบ: ทำแล้ว (เพดานส่งรวม และทดสอบ PUT ตั้งสถานะยืนยันกับของจริง)
3. merge เข้า main: ทำแล้ว
4. เปิดสวิตช์ยืนยันอีเมล: ทำแล้วเมื่อ 13 ต.ค. 2026 ตามคำสั่ง Master ผลบนระบบจริง signup คืน status verify ไม่ให้ token และล็อกอินก่อนยืนยันไม่ได้ ย้อนกลับด้วยการ deploy ซ้ำโดยตั้งค่าเป็น false (จุดถอยคือ deployment 73ac6f22)

## ความเสี่ยงและช่องว่างที่ยังเปิด
- รหัสผ่าน Gmail ที่เก็บไว้ยาว 19 ตัวและมีช่องว่าง ระบบตัดช่องว่างก่อนใช้ ส่งสำเร็จแล้วจึงถือว่าใช้ได้ แต่ควรตรวจซ้ำถ้าเปลี่ยนรหัส
- Gmail แบบบัญชีทั่วไปมีเพดานส่งต่อวัน ยังไม่ทราบตัวเลขจากเอกสารทางการ ระบบมีเพดานของตัวเองแล้ว (400 เป็นค่าเผื่อ ไม่ใช่เลขทางการ) เมลอาจเข้าสแปม ยังไม่ได้ตรวจอัตราเข้ากล่องสแปม
- ตัวจำกัดอัตราในหน่วยความจำของ Worker ไม่ใช่ตัวกันหลัก ตัวกันหลักคือฐานข้อมูล
- ยังไม่ได้วัดว่าอีเมลที่ส่งจากบัญชี Gmail นี้เข้ากล่องหลักหรือสแปมสำหรับผู้รับทั่วไป ถ้าผู้ใช้สมัครแล้วไม่ได้รับรหัส จะเข้าแอปไม่ได้ ต้องมีทางออก (ปุ่มส่งซ้ำมีแล้ว)

## วิธีเปลี่ยนค่าสวิตช์ (ตรวจแล้ว 13 ต.ค. 2026)
ตัวแปรนี้เป็นตัวแปรธรรมดา เปลี่ยนด้วย wrangler deploy พร้อม --keep-vars และประกาศ vars ในไฟล์ตั้งค่าของสำเนา build เท่านั้น เส้นทาง API สำหรับเพิ่ม secret ทีละตัวใช้ไม่ได้กับชื่อที่เป็นตัวแปรธรรมดาอยู่แล้ว (ตอบ 400 รหัส 10053) หลัง deploy ต้องเทียบชื่อ binding ก่อนและหลังทุกตัว และทดสอบ signup จริง

## สิ่งที่ Master ต้องทำเอง
- รัน SQL ที่ตกลงกันไว้ใน Supabase SQL Editor (ทำแล้วสำหรับ migration 004) เอเจนต์ต้อง push ไฟล์ขึ้น GitHub ก่อนบอกให้รันเสมอ
