# S3 ครอบด้วย Next.js (ช่วง: กลาง รายละเอียดบางส่วน)

กลับไปที่ [แผนหลัก](../MASTER-PLAN.md) | ขั้นก่อนหน้า [S2](S2-notify-ai.md) | ขั้นถัดไป [S4](S4-typescript.md)

## เป้าหมาย
แอปเดิมทำงานเหมือนเดิมทุกอย่างเมื่ออยู่บน Next.js แบบ static export โดยยังใช้แม่แบบหน้าเดิม ยังไม่แปลงเป็น React

## ผลลัพธ์ที่ตรวจได้
1. ภาพหน้าจอเหมือนต้นฉบับ 0 พิกเซล
2. ชุดทดสอบ route 22 ข้อ และชุดทดสอบฟีเจอร์ 13 ข้อ ผ่านครบ
3. ใช้งานออฟไลน์ได้ รวมปฏิทินที่เก็บไฟล์เองไว้ในเครื่อง
4. service worker ทำงานและแคชครบ ไม่ทำให้ผู้ใช้เห็นหน้าเก่าค้าง

## ข้อเท็จจริงที่ตรวจแล้ว
- ES module ของ 25 ไฟล์ (27 สคริปต์ชนิดโมดูล) ผ่านประตู 5 ชุดและ deploy แล้ว (app-esm2, SW v44) นี่คือฐานของขั้นนี้
- ยังไม่มีไฟล์ Next.js หรือ React ในที่เก็บ (ตรวจ 16 ต.ค. 2026) การทดลองทำในโฟลเดอร์ชั่วคราวนอกรีโปทั้งหมด
- วัดจริง 16 ต.ค. 2026 บนเครื่องนี้: ติดตั้ง Next.js 16.4.2 กับ React 19.3.1 ใช้ 9 วินาที build ใช้ 2 วินาที
- ขนาดแอปปัจจุบัน 40 ไฟล์ 503 KB (โมดูล 26 ไฟล์ 144 KB, CSS 44 KB)
- Next.js ปล่อยไฟล์ในโฟลเดอร์ public ผ่านตรงทุกไบต์ ทดลองแล้ว 40 จาก 40 ไฟล์เหมือนเดิม เมื่อไม่มีหน้า / ของ Next (ถ้ามี app/page.js มันเขียนทับ index.html ของเรา แอปไม่บูต)
- ผลส่งออก 49 ไฟล์ 1,059 KB (Next เพิ่ม 9 ไฟล์ใต้ _next ที่แอปไม่เรียก) เพดาน Static Assets 20,000 ไฟล์ ห่างมาก
- ประตูทั้งสี่ผ่านครบกับผลส่งออกของ Next ใต้โดเมน forge: ภาพ 20/20, route 22/22, feature 13/13, ออฟไลน์ 8/8 นี่พิสูจน์แนวทางเชิงโครงสร้างเท่านั้น ยังไม่ใช่การ deploy จริง

## สิ่งที่ยังไม่ทราบ
- header ที่ Cloudflare ส่งให้ sw.js และ manifest หลัง deploy จริงผ่าน build ใหม่ (ทดสอบได้เฉพาะเมื่อ deploy forge)
- service worker ของเครื่องที่ใช้อยู่แล้ว (v46 ถึง v47) จะอัปเดตเป็นรุ่นใหม่โดยไม่เห็นหน้าเก่าค้างหรือไม่ ต้องทดสอบด้วยเครื่องที่มีแคชเก่า
- เวลาที่ใช้จริงของขั้นลงมือ ยังไม่เคยทำ ประเมินจากส่วนที่วัดแล้วด้านบนว่าน้อยกว่าที่เคยกลัว แต่ยังไม่ใช่ค่าที่วัดจากการทำจริง

## แผนลงมือ (เขียน 16 ต.ค. 2026)

แนวทาง: ครอบด้วย Next.js แบบปล่อยไฟล์เดิมผ่านตรงๆ ไม่แตะโค้ดแอปสักไบต์ ไฟล์ทั้งหมดของแอปอยู่ในโฟลเดอร์ public ของ Next และไม่มีหน้า / ของ Next
seam คือโฟลเดอร์ public (ฝั่งแอปเดิม) กับขั้น export (ฝั่ง Next) แอปเดิมไม่รู้ว่า Next มีอยู่

ขั้นย่อย เรียงตามลำดับ:
1. สร้างโครง Next ในรีโป: next.config.mjs (output export), app/layout.js, app/not-found.js, package.json (เพิ่ม next react react-dom) ห้ามมี app/page.js
2. สคริปต์ build คัดลอก app/web เข้า public ชั่วคราว (public อยู่ใน .gitignore) ไฟล์แอปคงอยู่ที่ app/web ที่เดียว
3. แก้ scripts/build-web.mjs: next build แล้วค่อยฉีดบรรทัด EVAREL_API เข้า index.html ใน out ส่งต่อไป build/web ไม่ต้องแก้ wrangler.toml
4. ประตูทดสอบที่ใช้ EVAREL_WEB_DIR ชี้ไป out ผ่านครบ 4 ชุดบวกประตูโครงสร้าง
5. deploy forge แล้วทดสอบ header ของ sw.js กับ manifest และทดสอบอัปเดต service worker จากรุ่นเก่า
6. ขยับ sw VERSION ปิดสัญญา แล้วจึงไป S5

ข้อตัดสินใจที่ตรวจแล้ว (ไม่ต้องรอ Master): Next.js ไม่มีตัวเลือกตั้งพาธ public (ซอร์สกำหนดตายตัวที่ public ใต้โฟลเดอร์โปรเจกต์) ทางเลี่ยงด้วยลิงก์สัญลักษณ์ใช้ได้บนเครื่องนี้ แต่ไม่แน่ใจกับ Windows และ CI ของ Cloudflare จึงเลือกทางที่ไม่พึ่งลิงก์: ให้สคริปต์ build คัดลอก app/web เข้า public ชั่วคราว แล้ว next build แล้วลบ public ทิ้ง ไม่เก็บ public ใน git ไฟล์แอปคงอยู่ที่ app/web ที่เดียว ไม่ย้ายพาธ ประตูทดสอบและเครื่องมือเดิมไม่ต้องแก้พาธ

ย้อนกลับ (ตอบเช็กลิสต์ grillme ข้อ Rollback): ทุกอย่างอยู่บนสาขา develop ย้อนด้วย git revert ได้ scripts/build-web.mjs เดิมไม่ถูกลบจนกว่าประตูทั้งหมดผ่านกับ build ใหม่ การ deploy forge ทำหลังประตูผ่านเท่านั้น และ deploy ก่อนหน้ายังใช้งานได้จนกว่าจะเปลี่ยน

ความเสี่ยงที่ต้องคุม:
- ถ้ามี app/page.js ใดๆ ปรากฏขึ้นภายหลัง index.html จะถูกเขียนทับเงียบๆ ควรเพิ่มตัวตรวจใน build ว่า out/index.html ตรงกับต้นทางทุกไบต์ ก่อนฉีด API
- ไฟล์ตั้งค่าเครื่องมือที่ฝังชื่อโมดูลและพาธ (ประตูทดสอบ, tools) เปลี่ยนเลขลำดับแล้วเมื่อ 16 ต.ค. ตรวจซ้ำว่าไม่มีตัวไหนอ้างชื่อเก่า
