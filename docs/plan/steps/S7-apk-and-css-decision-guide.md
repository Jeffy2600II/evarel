> **สถานะ:** เอกสารนี้เป็นข้อมูลประกอบการตัดสินใจ ณ 15 ต.ค. 2026 ซึ่ง Master ตัดสินแล้วว่าใช้ **React Native** (APK) และ **Tailwind** (CSS) ข้อความในเอกสารที่แนะนำ Capacitor หรือ CSS Modules คือข้อเสนอก่อนตัดสิน **ไม่ใช่แผนปัจจุบัน** แผนจริงอยู่ที่ [S7-apk-react-native.md](S7-apk-react-native.md) และ [S5-react-pages.md](S5-react-pages.md)

## ส่วน ก: สร้างแอป APK

### ก.1 ตอนนี้ Evarel เป็นอะไรอยู่
Evarel ตอนนี้เป็น **PWA** (Progressive Web App) คือเว็บที่ติดตั้งลงหน้าจอหลักของมือถือได้และทำงานเหมือนแอป เปิดผ่านเบราว์เซอร์ Chrome ของเครื่องอยู่เบื้องหลัง manifest ของแอปตั้งเป็นเต็มจอ (`display: standalone`) แนวตั้ง (`portrait`) สี `#4B2FF5` [วัดจากไฟล์ manifest.webmanifest]

**APK** คือไฟล์ติดตั้งแอปของ Android (เหมือนไฟล์ .exe ของ Windows) เมื่อมีไฟล์นี้ ผู้ใช้ติดตั้งแล้วแอปจะมีไอคอนของตัวเองและทำงานแยกจากเบราว์เซอร์

### ก.2 คำศัพท์ที่จะเจอ (อ่านครั้งเดียวจบ)

| คำ | คืออะไร (ภาษาคน) | ตัวอย่างเปรียบเทียบ |
|---|---|---|
| React | เครื่องมือเขียนหน้าจอแบบประกอบชิ้นส่วน (ปุ่ม การ์ด รายการ) ตัวมันไม่รู้ว่าจะแสดงผลที่ไหน | ตัวต่อเลโก้ ยังไม่ใช่ของสำเร็จรูป |
| Next.js | ชุดเครื่องมือสำเร็จรูปสร้างบน React สำหรับ **เว็บ** ช่วยจัดหน้า จัดเส้นทาง และ build ผลลัพธ์เป็นไฟล์เว็บ | ชุดเลโก้พร้อมแผ่นฐานและคู่มือ สำหรับสร้างบ้าน (เว็บ) |
| TypeScript | JavaScript ที่ต้องบอกชนิดข้อมูล ช่วยจับความผิดพลาดก่อนใช้งานจริง | การเช็กตัวสะกดก่อนส่งจดหมาย |
| React Native | React อีกรูปแบบที่วาดหน้าจอด้วยชิ้นส่วนของ Android จริงๆ ไม่ใช่เว็บ | ใช้เลโก้ตัวต่อชุดเดียวกัน แต่สร้างรถ ไม่ใช่บ้าน ต้องใช้ชิ้นส่วนคนละแบบ |
| Capacitor | ตัวห่อหุ้มเว็บของเราให้เป็นแอป เปิดหน้าเว็บในกรอบแอปและมีสะพานให้เรียกความสามารถของเครื่อง เช่น แจ้งเตือนในเครื่อง | เอาบ้านที่สร้างเสร็จใส่กรอบกระจกแล้วติดตั้งบนรถบรรทุก |
| TWA | แอปบางๆ ที่เปิด PWA ผ่าน Chrome เต็มจอ ไม่มีกรอบของตัวเอง | ทางลัดที่ดูเหมือนแอป |
| WebView | หน้าต่างเว็บเล็กๆ ในแอป (ตัวที่ Capacitor ใช้โชว์หน้าเว็บ) | จอทีวีที่ฝังอยู่ในแอป |
| Keystore / การเซ็นแอป | กุญแจดิจิทัลที่ยืนยันว่าแอปนี้เป็นของเรา ต้องใช้ทุกครั้งที่ปล่อยเวอร์ชันใหม่ | ตราประทับเจ้าของ หายแล้วอัปเดตแอปเดิมไม่ได้ |

### ก.3 ทำไม "React" กับ "React Native" ถึงไม่ใช่เรื่องเดียวกัน
สิ่งที่ Master ถามคือต่างกันยังไง คำตอบสั้นที่สุด:

- **React (แบบเว็บ)** สร้างหน้าจอด้วย HTML/CSS ซึ่งเป็นภาษาของเบราว์เซอร์ ผลคือเว็บ
- **React Native** สร้างหน้าจอด้วยชิ้นส่วนของ Android โดยตรง ไม่มี HTML ไม่มี CSS แบบเว็บ ปุ่มทุกปุ่มต้องเขียนด้วยชิ้นส่วนของมันเอง

ผลที่ตามมาคือ **โค้ดหน้าจอที่เราเขียนไว้แล้วใช้ต่อไม่ได้** เพราะมันเป็น HTML/CSS ถ้าเลือก React Native หน้าจอทุกหน้าของ Evarel ต้องเขียนใหม่ทั้งหมด เหลือใช้ร่วมกับเว็บได้แค่ส่วนที่ไม่ใช่หน้าจอ เช่น กฎการคำนวณเวลาแจ้งเตือน การคุยกับ AI การจัดการข้อมูล

### ก.4 สามทางที่ทำให้เป็น APK ได้จริง

**ทาง A: TWA (แอปบางที่เปิด PWA เดิม)**
เอา PWA ที่ใช้อยู่ ห่อด้วยแอปบางๆ ให้ได้ไฟล์ APK ง่ายที่สุด เร็วที่สุด แต่ควบคุมเครื่องได้น้อยที่สุด เพราะตัวแอปจริงๆ ยังคือ Chrome

**ทาง B: Capacitor ครอบเว็บ (ที่ผมแนะนำ)**
เอาเว็บที่ build แล้ว (ผลจาก Next.js ของแผน S3) ใส่ลงในแอปของ Capacitor ตัวแอปมีกรอบของตัวเองและมีปลั๊กอินเรียกความสามารถของเครื่องได้ ข้อกำหนดจากเอกสารทางการของ Capacitor [ตรวจจาก capacitorjs.com]: เว็บต้องมี `package.json`, โฟลเดอร์ที่ build แล้ว และไฟล์ `index.html` ที่มีแท็ก `<head>` ซึ่งโครงสร้างเว็บของ Evarel มีครบ รองรับ Android 7 ขึ้นไป (ราว 99% ของตลาดตามที่เอกสารระบุ)

**ทาง C: React Native**
สร้างแอปใหม่ด้วยชิ้นส่วนเนทีฟ ควบคุมเครื่องได้มากที่สุด แต่เท่ากับเริ่มสร้างหน้าจอทั้งชุดใหม่

### ก.6 ความเข้าใจเรื่อง "สองฝั่ง" ที่ Master พูดถึง
Master บอกว่าอยากให้ระบบมีสองฝั่ง คือแอปกับเว็บ หน้าตาและฟังก์ชันเหมือนกันเป๊ะ แต่ความแข็งแรงต่างกันตามแพลตฟอร์ม ผมเข้าใจเจตนาแบบนี้ ถ้าเข้าใจผิดให้แก้ได้:

- **ส่วนที่ต้องเหมือนกัน:** หน้าตาและฟังก์ชัน
- **ส่วนที่ปล่อยให้ต่างได้:** ชั้นล่างที่ผู้ใช้ไม่เห็น เช่น วิธีแจ้งเตือน (เว็บใช้ Web Push ส่วนแอปแจ้งเตือนในเครื่องได้โดยไม่พึ่งเซิร์ฟเวอร์) การเก็บข้อมูลออฟไลน์ ความเสถียรเมื่อระบบประหยัดแบตเตอรี่

ทาง B ทำให้เป็นแบบนี้ได้โดยโครงสร้าง เพราะหน้าจอเป็นโค้ดชุดเดียว ความต่างอยู่ที่ชั้นล่างผ่านปลั๊กอิน ส่วนทาง C ตรงข้ามกับเจตนานี้ เพราะหน้าจอจะกลายเป็นสองชุดที่ต้องคอยดูแลให้เหมือนกันตลอดไป

### ก.7 เรื่องที่ต้องรู้ก่อนตัดสินใจ

**การแจกจ่ายแอป (งบ 0 บาท)**
- **ไฟล์ตรง (GitHub Releases):** ฟรี ผู้ใช้ต้องเปิด "ติดตั้งจากแหล่งที่ไม่รู้จัก" ในเครื่อง เหมาะกับใช้คนเดียวหรือคนสนิท
- **Google Play:** มีค่าสมัครครั้งเดียว **25 ดอลลาร์สหรัฐ** [ตรวจจากหน้าทางการของ Google Play Console] ต้องยืนยันตัวตนด้วยบัตรประชาชนและบัตรเครดิตหรือเดบิตที่เป็นชื่อเดียวกัน (บัตรเติมเงินไม่รับ) และบัญชีส่วนบุคคลที่สร้างหลัง 13 พ.ย. 2023 ต้องผ่านเงื่อนไขการทดสอบก่อนเผยแพร่ **ข้อนี้ขัดกับกฎงบ 0 บาท** ต้องให้ Master ตัดสินเองถ้าต้องการ

**การเซ็นแอป (keystore)**
กุญแจนี้ต้องสร้างครั้งเดียว เก็บเป็นความลับ และสำรองไว้อย่างน้อยสองที่ ถ้าหายจะอัปเดตแอปเดิมไม่ได้ ผู้ใช้ต้องถอนแอปแล้วติดตั้งใหม่ ข้อมูลในเครื่องหาย

**การแจ้งเตือนในแอป**
- ถ้าใช้ Web Push เดิม (ที่ใช้อยู่ตอนนี้) แอปแบบ Capacitor รองรับได้ ไม่ต้องเปลี่ยนตัวส่ง
- ทางเลือกอื่นคือ Firebase Cloud Messaging (FCM) ตามเอกสารของ Capacitor แต่เพิ่มบริการภายนอกอีกตัว ยังไม่จำเป็นในตอนนี้

**การ build บนเครื่องผม**
ตรวจแล้ว: เครื่อง sandbox ที่ผมใช้ **ไม่มี Android SDK, Java, Gradle** [วัด: ตรวจเครื่องมือ 15 ต.ค. 2026] ผลคือผม build APK ในเครื่องนี้ไม่ได้ ทางออกที่เป็นไปได้คือ build บน GitHub Actions (เซิร์ฟเวอร์ของ GitHub) แต่ **ผมยังไม่เคยลองและยังไม่ได้ตรวจโควตาฟรีของ GitHub Actions** ถือเป็นสิ่งที่ยังไม่ทราบ ต้องลองจริงก่อน

### ก.8 ความสัมพันธ์กับแผนปัจจุบัน
- S3 (ครอบด้วย Next.js แบบ static export) และ S5 (แปลงเป็น React ทีละหน้า) **ไม่ขัดกับ APK** ทาง B ใช้ผลผลิตของ S3 ได้ทันที
- ถ้า S5 ถูกเลื่อน APK ยังทำได้จากผลของ S3
- React Native ไม่ใช่การต่อยอดจากแผนปัจจุบัน แต่คือการเปลี่ยนทิศ

## ส่วน ข: เฟรมเวิร์ค CSS

### ข.1 CSS คืออะไร และ "เฟรมเวิร์ค" ช่วยอะไร
CSS คือภาษาที่กำหนดหน้าตา (สี ระยะห่าง มุมโค้ง ขนาดตัวอักษร) **เฟรมเวิร์ค CSS** คือชุดกฎและชิ้นส่วนสำเร็จรูปที่ช่วยให้ไม่ต้องเขียนทุกอย่างเอง

### ข.2 สถานะ CSS ของ Evarel ตอนนี้ (วัดจากโค้ดจริง 15 ต.ค. 2026)

| ตัวชี้วัด | ค่า | ความหมาย |
|---|---|---|
| ไฟล์ CSS | 1 ไฟล์ 339 บรรทัด | ไม่ใหญ่มาก |
| class ที่ประกาศ | 183 | จำนวนชิ้นส่วนหน้าตา |
| ค่า px ฝังตรง | 563 จุด ต่างกัน 58 ค่า | ระยะห่างและขนาดไม่มีระบบกลาง |
| ค่าที่ซ้ำมากสุด | 14px (49 ครั้ง), 12px (48), 6px (42), 8px (30), 16px (28) | มีค่าที่ใกล้กันแต่ไม่เท่ากันหลายตัว |
| ขนาดมุมโค้ง (border-radius) | 27 แบบต่างกัน | ความโค้งไม่สม่ำเสมอ |
| ขนาดตัวอักษร | 30 แบบต่างกัน | ลำดับชั้นตัวอักษรไม่เป็นระบบ |
| สี hex ฝังตรง | 53 จุด ต่างกัน 29 สี | สีบางส่วนไม่ผ่านตัวแปรกลาง |
| เงา (box-shadow) | 21 แบบต่างกัน | เงาไม่เป็นระดับ |
| ตัวแปร (design token) | 45 ตัว | มีฐานอยู่แล้วแต่ครอบไม่ทั่ว |
| สไตล์ฝังในโค้ด (`style="..."`) | 54 จุด | หน้าตาบางส่วนอยู่นอกไฟล์ CSS |
| จุดที่โค้ด JavaScript สร้าง HTML พร้อม class | 365 จุด | หน้าตาผูกกับชื่อ class ในโค้ดอย่างแน่น |

**ข้อสรุปจากตัวเลข:** อาการ "คุมยาก ทำให้เหมือนแอปไม่ได้" มีต้นเหตุจริง คือค่าหน้าตากระจายไม่เป็นระบบ (58 ค่าระยะ, 27 มุมโค้ง, 30 ขนาดตัวอักษร, 21 เงา) ในระบบดีไซน์ที่ดีมักมีแค่ 8 ถึง 12 ขั้นสำหรับแต่ละอย่าง การมีหลายสิบแบบทำให้ทุกครั้งที่ปรับต้องเดาว่าควรเลือกค่าไหน

### ข.3 ความจริงที่ต้องรู้ก่อน: เฟรมเวิร์คไม่ได้แก้ปัญหาได้เอง
ปัญหาแท้จริงคือ **ไม่มีระบบกลาง (design tokens ที่ครอบไม่ทั่ว)** ไม่ใช่ว่า CSS ขาดเครื่องมือ เฟรมเวิร์คจะช่วยได้ก็ต่อเมื่อเรา **กำหนดระบบกลางก่อน** (ระยะห่างกี่ขั้น มุมโค้งกี่ขั้น ฯลฯ) แล้วให้เฟรมเวิร์คบังคับใช้ ถ้าเอาเฟรมเวิร์คมาใส่โดยไม่กำหนดระบบ ค่ากระจัดกระจายเดิมจะย้ายเข้าไปอยู่ในรูปแบบใหม่ และยังคุมยากเหมือนเดิม

### ข.4 ข้อจำกัดใหญ่ที่สุด: ประตู "ภาพเหมือน 0 พิกเซล"
ประตูของ Master บังคับว่าหน้าตาต้องเหมือนต้นฉบับ 0 พิกเซล นั่นแปลว่า **เฟรมเวิร์คต้องสร้างผลลัพธ์เดิมเป๊ะ** ห้ามขยับแม้ 1 พิกเซล ปัญหาคือโค้ดปัจจุบันมีค่าอย่าง 14px และ 15px, 5px และ 6px อยู่ใกล้กันโดยตั้งใจหรือไม่ก็ตาม ถ้าเราบังคับให้ใช้ระบบ 8 ขั้นที่สม่ำเสมอ ค่าที่ไม่ตรงขั้นจะต้องปัดเป็นค่าใกล้สุด ซึ่งทำให้ภาพขยับและประตูตก

ทางออกมีสองแนว:
1. **ทำแบบอนุรักษ์:** เฟรมเวิร์คต้องรองรับ "ค่าเฉพาะ" ได้ (เช่น ระยะ 14px ที่มีอยู่เดิมกลายเป็นขั้นหนึ่งในระบบ) ได้ผลเดิมเป๊ะ แต่ระบบจะมีขั้นเยอะกว่าระบบมาตรฐาน
2. **ทำแบบปรับปรุง:** ยอมให้หน้าตาขยับเล็กน้อยเข้าสู่ระบบที่สม่ำเสมอ แล้วอัปเดตภาพต้นฉบับใหม่ ซึ่งขัดกับกฎ "ดีไซน์ canonical ของ Master ห้ามเปลี่ยนเอง" ต้องให้ Master อนุญาตชัดเจน

### ข.5 ตัวเลือกเฟรมเวิร์ค (เปรียบเทียบแบบเข้าใจง่าย)

| ตัวเลือก | แนวคิด | ข้อดี | ข้อเสีย | เข้ากับกฎ 0 พิกเซล |
|---|---|---|---|---|
| **Tailwind CSS** | เขียน class สั้นๆ ติดบนชิ้นส่วนโดยตรง (เช่น ระยะห่าง 4 หน่วย) มีระบบขั้นระยะ/สี/ขนาดในตัว | ระบบกลางชัด นิยมสูง เอกสารเยอะ เข้ากับ Next.js และ React ดี | ต้องแก้ทุกจุดที่เขียน class (365 จุดในโค้ด) โค้ดอ่านดูรก ต้องมีขั้นตอน build | ได้ถ้าตั้งค่าให้ตรงค่าเดิม แต่ต้องทำงานเยอะ |
| **CSS Modules** | แต่ละชิ้นส่วนมีไฟล์ CSS ของตัวเอง ชื่อ class ไม่ชนกัน | ใช้ CSS ปกติได้ ไม่ต้องเรียนภาษาใหม่ เข้ากับ Next.js ในตัว ย้ายทีละหน้าได้ดี (เหมาะกับ S5) | ไม่ได้ให้ระบบขั้นระยะ/สีมาให้ ต้องสร้างเอง | ดีที่สุด เพราะคัดลอกค่าเดิมได้ตรงๆ |
| **CSS ปกติ + design tokens ให้ครบ** | ไม่เพิ่มเครื่องมือ แต่เก็บทุกค่าเป็นตัวแปรกลาง | ไม่เพิ่มความเสี่ยง ใช้ได้ทันที ไม่ผูกกับเฟรมเวิร์ค | ต้องมีวินัยเอง ไม่มีใครบังคับ | ดีที่สุด (ไม่เปลี่ยนหน้าตา) |
| **UnoCSS / อื่นๆ** | คล้าย Tailwind | เร็ว ยืดหยุ่น | ชุมชนเล็กกว่า ข้อมูลน้อยกว่า | เหมือน Tailwind |

**ข้อสังเกตที่ผมประเมินจากข้อมูลข้างบน (เป็นความเห็น ไม่ใช่ข้อเท็จจริง):** สำหรับ Evarel ที่ต้องรักษาภาพ 0 พิกเซลและกำลังจะย้ายไป React ทีละหน้า การรวม "design tokens ให้ครบ" ก่อน แล้วใช้ CSS Modules ตอนแปลงแต่ละหน้า ดูมีความเสี่ยงต่ำที่สุด Tailwind ทำให้ได้ระบบที่เข้มแข็งกว่าในระยะยาว แต่ราคาคือต้องรื้อทุกจุดที่เขียน class และเสี่ยงต่อประตูภาพมากกว่า

### ข.6 เรื่องที่เฟรมเวิร์ค CSS ไม่ช่วย
ความรู้สึก "เป็นแอป" ไม่ได้มาจาก CSS อย่างเดียว ต้องแก้ที่พฤติกรรมของหน้าเว็บด้วย:
- เลื่อนแล้วไม่เด้งแบบเว็บ (overscroll)
- แตะแล้วมีตอบสนองทันที ไม่มีหน่วง
- เลือกข้อความโดยไม่ตั้งใจ
- พื้นที่ขอบจอ (safe area) ซึ่งโค้ดปัจจุบันมีแล้ว

เรื่องเหล่านี้แก้ได้โดยไม่ต้องเปลี่ยนเฟรมเวิร์ค

- ถ้าเลือก Tailwind จะต้องแก้กี่จุดจริง (ตัวเลข 365 จุดนับเฉพาะ class= ใน JS ยังไม่ได้นับจุดอื่น)
