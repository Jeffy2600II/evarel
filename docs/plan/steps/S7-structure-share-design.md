# โครงสร้างระบบปัจจุบันและการแบ่งชั้นเผื่อแอป (ตรวจจากโค้ดจริง 31 ต.ค. 2026)

กลับไปที่ [แผนหลัก](../MASTER-PLAN.md) | [S7 แอป APK](S7-apk-react-native.md) | [คู่มือตัดสินใจ S7](S7-apk-and-css-decision-guide.md)

## ที่มา

คำถามของ Master (31 ต.ค. 2026): เข้าไปดูแล้วยังมีโฟลเดอร์ web อยู่ข้างในโฟลเดอร์ app ทำไม, การออกแบบที่วางไว้เผื่อทำแอปในอนาคตมีความซ้ำซ้อนกันหรือไม่, มีเพจและส่วนต่าง ๆ ที่อาจไม่ถูกแอปใช้จริง, ควรย้ายหรือแบ่งใหม่อย่างไร

วิธีตรวจ: สแกนโซร์สจริงทั้ง app/src/core (23 ไฟล์) และโซนหน้าจอ (app/src/react + app/pages + app/shared) นับจุดผูกเบราว์เซอร์ (document, window, navigator, localStorage, Notification, serviceWorker, location, ชนิด DOM, ตัวผลิตสตริง HTML) ต่อไฟล์ แล้วไล่ผู้อ้างถึงโฟลเดอร์ที่สงสัย (app/web, web-shell, web-next, app-v13, design/) จากสคริปต์ ทดสอบ เครื่องมือ เวิร์กโฟลว์ และคอนฟิกทั้งหมด ณ commit 54465c9 (2026.2.60)

## 2) ตอบตรงคำถาม: ทำไม app ถึงมี web อยู่ข้างใน

1. **คนละความหมายของคำว่า app** โฟลเดอร์ `app/` ในที่นี้แปลว่า "โฟลเดอร์แอปพลิเคชันทางการ" (มีทั้งหลังบ้าน api/db/edge และหน้าบ้าน) ไม่ใช่ "แอปมือถือ" ตามแผน S7 — ชื่อจึงชนกับความหมายที่ Master ใช้พูดถึงแอปในอนาคต
2. **`app/web/` ไม่ใช่ของเกิน และยังไม่ควรย้ายตอนนี้** เพราะมันทำงานสามบทบาทพร้อมกัน:
   - **แหล่งโมดูลคอมไพล์แล้วที่ Next กินเข้าบันเดิล** — `web-next/src/lib/boot.ts` import ไฟล์ใน `app/web/js/react/*` (17 ไฟล์) และ `app/web/js/app/*` (26 โมดูล) เข้าบันเดิลของ Next โดยตรง (ไบต์ N1 ล็อกลำดับโหลดไว้เพื่อพิสูจน์ความเท่าเดิมด้วยการคำนวณ)
   - **ตัวตั้งของประตูและทดสอบ 87 ไฟล์** — ชุดภาพพาริตี ชุด equiv ทุกตัว โหลดโมดูลจากพาธ `app/web/...` โดยตรง
   - **เอกสารสถานะเดิมของเว็บคลาสสิก** — index.html + sw.js ฉบับก่อน S4 ยังเก็บไว้เป็นหลักฐานและเส้นทางถอยกลับ
3. **เส้นทางเสิร์ฟจริงปัจจุบันไม่ใช่ app/web แล้ว** ตั้งแต่ S4 ผ่าน: `web-next` build ออกมาเป็น `build/web` แล้ว deploy ด้วย wrangler (deploy.mjs) และตัวตรวจใน build-web.mjs ห้ามมีโมดูล window เดิมในเส้นทางเสิร์ฟ — สิ่งที่ผู้ใช้เปิดอยู่คือ Next

## 3) ความซ้ำซ้อนที่ตรวจพบ (ตัดสินจากผู้อ้างถึงจริง ไม่ใช่ความรู้สึก)

| ประเภท | รายการ | ข้อเสนอ |
|---|---|---|
| ชื่อชนแต่ของไม่ซ้ำ | `app/web` (คำอธิบายในข้อ 2) | ไม่ย้ายตอนนี้ 87 ไฟล์อ้างพาธอยู่ ย้ายพร้อมกันตอนปิด S6 ถ้า Master อนุมัติ |
| ซ้ำซ้อนเชิงประวัติศาสตร์ แต่ยังจำเป็น | `web-shell` — ถูก web-next แทนบทบาทหน้าบ้านแล้ว แต่ node_modules react/react-dom ของมันยังถูก build-react อ้างด้วย alias และทดสอบ s3_next_wrap ยังอ้าง | เก็บไว้จนกว่าจะย้าย react/react-dom มาที่เดียวกับ web-next (หรือราก) แล้วจึงย้ายเข้า archive พร้อมกับ S6 |

**สรุป: ยังไม่พบของเกินที่ต้องลบทันที** สิ่งที่เจอคือ (ก) ชื่อโฟลเดอร์ชนกับความหมายของ "แอป" (ข) ของเก่าที่แผน S6 มีคิวย้ายเข้า archive อยู่แล้ว (ค) บทบาทซ้ำระหว่างสองหน้าบ้านที่ตามแผนแล้ว Next ชนะไปและเหลือแต่ความจำเป็นในการบันเดิล

## 4) ผลตรวจว่าตรรกะส่วนไหนใช้กับแอปได้จริง (ปิดข้อสงสัยเดิมข้อสุดท้ายของ S7)

S7 เดิมระบุไว้ว่า "ตรรกะส่วนไหนแยกออกมาใช้ร่วมกับเว็บได้จริง ต้องตรวจโค้ดก่อนว่าผูกกับเบราว์เซอร์ (DOM) มากแค่ไหน" — ตรวจแล้ว ณ 31 ต.ค. 2026 ด้วยการสแกนแบบนิ่ง (static) ทั้ง 23 ไฟล์ เกณฑ์คือ React Native ไม่มี DOM, window, document, localStorage, Notification API, serviceWorker, location และไม่เรนเดอร์สตริง HTML แต่มี fetch, setTimeout/setInterval, JSON, Date, crypto.subtle เหมือนเบราว์เซอร์

| กลุ่ม | จำนวน | ไฟล์ | ความหมายกับแอป |
|---|---|---|---|
| ก. ตรรกะล้วน ใช้ร่วมทันที | **13 (57%)** | aiproposal, avatar, calendar, dates, form, markdown, repo, schedule, stats, store, today, authform, ailive (ผูกแค่ setTimeout ซึ่ง RN มีในตัว) | แอป import ใช้ได้เลย ไม่ต้องแก้ — รวม repo.ts (ชั้นข้อมูลทั้งระบบ ใช้ fetch ล้วน) ที่แอปจะใช้ต่อเหนือ Supabase/Worker ชุดเดิม |
| ข. ใช้ร่วมบางส่วน — ต้องแยก "โรงงาน HTML" ออก | **7 (30%)** | constants (seg/icon ผลิต SVG+ปุ่ม), popover (popPlace คณิตล้วนใช้ร่วมได้ / popItemsHTML เว็บ), undo (toastHTML), quota (กติกาโควตาใช้ร่วมได้ / limit+sheet HTML), authviews, settingsviews, uihtml (โรงงาน HTML ทั้งไฟล์) | กติกาในไฟล์พวกนี้ยังใช้ต่อได้ แต่ผลลัพธ์เป็นสตริง HTML ที่แอปเรนเดอร์ไม่ได้ ต้องตัดฟังก์ชันผลิต HTML ออกไปอยู่ฝั่งเว็บเท่านั้น (งานแยกไฟล์ละ 1 ครั้ง ผ่านชุด equiv เดิมได้) |
| ค. ผูกเบราว์เซอร์ ต้องทำ adapter | **3 (13%)** | authclient (localStorage 3 จุด + location 4 จุด), notify (localStorage 1 + Notification/Push/SW 3), timer (localStorage 1) | ต้องมีจุดต่อกลาง (storage, session/redirect, notification) ที่เว็บและแอปใส่ฉบับของตัวเอง โค้ดตรรกะในไฟล์คงอยู่ครบ แก้เฉพาะจุดอ่าน/เขียน |

**สรุปเชิงตัวเลข:** ตรรกะของระบบที่แอปใช้ต่อได้จริง = 20/23 ไฟล์ (87%) โดยไม่ต้องเขียนใหม่ มีแค่แยกโรงงาน HTML ออกจากกลุ่ม ข หรือทำ adapter กลุ่ม ค — ส่วนหน้าจอ (react zones + เครื่องยนต์ + uihtml) แอปไม่ใช้ตามการตัดสินเดิมของ Master ใน S7 ที่ให้เขียนหน้าจอใหม่ และ react/store.js (ตัวนับรอบ subscribe ล้วน) เป็นของโซนหน้าจอที่ใช้ร่วมได้แต่มีค่าน้อยมากถ้าแยกไป

ข้อจำกัดของผลตรวจนี้: เป็นการสแกนแบบนิ่ง ยังไม่รันจริงบน RN — ก่อนถือเป็นข้อเท็จจริงเด็ดขาด ให้ยึดหลักเดิมของแผน: ต้องพิสูจน์ด้วยการ import ทดลองกลุ่ม ก ในโครง RN จริงก่อน (อย่างน้อย dates/schedule/stats/form)

## 5) การออกแบบ 3 ชั้นเผื่อแอป (เป้าหมายเมื่อทำ S7)

```
ชั้น 3  หน้าจอ (ต่อแพลตฟอร์ม เขียนแยก ไม่แชร์)
        เว็บ: app/src/app + โซน react (pages/shared/data) + โรงงาน HTML (uihtml ฯลฯ)
        แอป: React Native (TSX) — เขียนใหม่ตามที่ Master ตัดสินไว้แล้ว 15 ต.ค. 2026
ชั้น 2  adapter (interface เดียว ฉบับต่อแพลตฟอร์ม)
        storage: เว็บ = localStorage | แอป = AsyncStorage/SecureStore (ยังไม่ได้เลือก)
        session/redirect: เว็บ = location | แอป = navigation ของ RN
        notification: เว็บ = SW + Web Push (ของเดิม) | แอป = FCM หรือ local (ยังไม่ได้ตัดสิน ตาม S7)
ชั้น 1  แชร์ (ชุดเดียวทั้งระบบ ห้ามมีสำเนา)
        app/src/core กลุ่ม ก (13 ไฟล์) + กลุ่ม ข หลังตัดโรงงาน HTML (กติกา 6 ไฟล์)
        หลังบ้าน app/api + app/db + app/edge ใช้ร่วม 100% ผ่าน HTTP/Repo adapter ชุดเดิม
```

ภาษาของแอป: S7 ล็อก **React Native** ซึ่งเขียนด้วย TypeScript — ตรงกับ core ที่เป็น TS อยู่แล้วทุกไฟล์ จึงแชร์โค้ดชั้น 1 ได้แบบ import ตรง ไม่ต้องพอร์ตข้ามภาษา (นี่คือเหตุผลที่ผลตรวจข้อ 4 มีค่า: 87% ของตรรกะอยู่ในภาษาเดียวกับแอปแล้ว)

### ทางเลือกโครงสร้างโฟลเดอร์ (รอ Master รับรองก่อนลงมือ)

| ทางเลือก | ทำอะไร | ผลข้างเคียง | เมื่อไร |
|---|---|---|---|
| **B — เพิ่มโดยไม่ย้าย (แนะนำทำก่อน)** | คงโครงปัจจุบันทั้งหมด สร้างโฟลเดอร์แอปใหม่ระดับราก (เช่น `mobile/`) ที่ import จาก `app/src/core` ตรง ๆ และเปิดจุดต่อ adapter ใน core | เกือบเป็นศูนย์: 87 ไฟล์ทดสอบและประตูทุกชุดไม่ถูกแตะ | เริ่ม S7 ได้ทันที |
| A — ย้ายจริง (จัดโครงใหม่ทั้งราก) | แบ่งเป็น `packages/core`, `platforms/web` (app/web + web-next), `platforms/mobile`, `backend` (api/db/edge), `archive/` (app-v13, design เดโม) | ต้องแก้ผู้อ้างพาธ 87+ ไฟล์ รันประตูทุกชุดใหม่ และต้องมีจุดถอยกลับระบุเวอร์ชัน (ตรงเกณฑ์ S6 ข้อ 3) | ตอนปิด S6 พร้อมกับการย้ายโฟลเดอร์ทดลองเข้า archive ที่แผนคิวไว้แล้ว |

คำแนะนำ: ทำ B ก่อนเสมอ แล้วสะสม adapter ชั้น 2 ระหว่างทาง เมื่อถึง S6 ค่อยตัดสินว่าคุ้มย้าย A หรือไม่ (เพราะ A และเป้าย้าย archive ของ S6 ควรทำรวมกันครั้งเดียว ไม่รื้อสองรอบ) การตัดสินเป็นของ Master ตามกติกาแผนหลัก

## 6) ข้อเสนอขั้นถัดไป (รอ Master รับรอง)

1. **แยกโรงงาน HTML ออกจากกลุ่ม ข (7 ไฟล์ → คงกติกาไว้ใน core)** — ทำทีละไฟล์ผ่านชุด equiv เดิม ไม่มีการเปลี่ยนพฤติกรรม ทำให้ core กลายเป็นชุดที่แอป import ได้ทั้งก้อน (ยกเว้นกลุ่ม ค)
2. **เปิดจุดต่อ adapter ในกลุ่ม ค (3 ไฟล์)** — นิยาม interface storage/redirect/notification ให้เว็บใส่ฉบับเดิมของตัวเองก่อน (พฤติกรรมไม่เปลี่ยน ผ่านประตูทุกชุด) แอปค่อยใส่ฉบับตัวเองตอน S7
3. **S6: ย้าย app-v13 และ design เดโมเข้า archive พร้อมแก้ผู้อ้าง 23 ไฟล์** และยุบ web-shell หลังย้าย react/react-dom ไปที่เดียวกับ web-next
4. **S7: สร้าง `mobile/` ตามทางเลือก B** — พิสูจน์ด้วยการ import กลุ่ม ก จริง (dates, schedule, stats, form ก่อน) แล้วค่อยขยาย
5. ห้ามย้าย/เปลี่ยนชื่อ `app/web` ตอนนี้เด็ดขาด — ทำพร้อมกับข้อ 3 ในครั้งเดียวถ้าจะทำ

## 7) สิ่งที่ยังไม่ทราบ (ต้องวัดหรือตรวจก่อนอ้างเป็นข้อเท็จจริง)

- ผลตรวจข้อ 4 เป็นการสแกนแบบนิ่ง ยังไม่เคยรัน core บน React Native จริง (ต้องพิสูจน์ด้วยโครงทดลองก่อนถือเป็นข้อเท็จจริง)
- เงื่อนไขโควตาฟรีของ EAS Build / GitHub Actions สำหรับ build APK ยังไม่ได้ตรวจ (อยู่ใน S7 เดิมแล้ว)
- เมื่อ S5 เปลี่ยนหน้าเป็น Tailwind ครบ ควรประเมินซ้ำว่า app/web เหลือบทบาทใดจริง (แหล่งบันเดิลยังอยู่ไหม)
- ทางเลือก AsyncStorage หรือ SecureStore ของแอป และ FCM หรือ local notification ยังไม่ได้ตัดสิน (เป็นของ S7 เดิม)
