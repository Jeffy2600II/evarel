# แผนระบบอัปเดตเว็บ Evarel (วางแผนเท่านั้น ยังไม่ได้สร้าง)

สถานะ: ร่างแผน ตามคำสั่ง Master 22 ต.ค. 2026 ("แค่วางแผนไว้ ยังไม่ได้ทำ")

## ขอบเขต (Master สั่ง 22 ต.ค. 2026)
- **เว็บ (ทำก่อน):** ยึดตาม build ปกติ ผู้ใช้ refresh ครั้งเดียวได้รุ่นใหม่ทันที พร้อม popup เต็มหน้าต่างและโน้ตรุ่น
- **แอปมือถือ (วางแผนไว้ ยังไม่ทำ):** ยึดตามการปล่อยรุ่น (release) ไม่ยึด build และแจ้งเตือนว่ามีรุ่นใหม่ ฐานของเว็บต้องออกแบบให้ต่อยอดได้ (ใช้ `release.json` และ GitHub Releases ตามข้อ 6)
- ตอนนี้ลงมือเฉพาะส่วนเว็บ ส่วนแอปเว้นที่ไว้เท่านั้น

## เป้าหมาย (คำของ Master)
1. ผู้ใช้ refresh แล้วได้เวอร์ชันใหม่ทันที ไม่ว่าอัปเดตแบบไหน
2. มีหน้าต่าง popup เต็ม (modal) บอกว่าอัปเดตอะไรใหม่ ไม่ใช่ toast เล็ก
3. ทุกอัปเดตมีโน้ตรุ่นเขียนไว้ บอกว่ามีอะไรใหม่ ปรับอะไร
4. ใช้ GitHub (Actions/workflow) เป็นตัวช่วย และเป็นฐานให้ระบบแจ้งเตือนอัปเดตในแอปต่อได้

## ของที่มีอยู่แล้ว (ตรวจจากโค้ดจริง 22 ต.ค. 2026)
- `build-next.mjs` สร้าง `sw.js` โดยแทน VERSION เป็นแฮชของ build (`evarel-next-<digest>`) ทุก build
- `sw.js` ใช้ `skipWaiting` + `clients.claim` + ลบแคชเก่าตอน activate
- `sw.js` ใช้ stale-while-revalidate: เปิดจากแคชก่อน ดึงใหม่เบื้องหลัง แล้วส่ง `update-ready` ถ้าไฟล์ต่างจากเดิม
- `boot.js` รับ `update-ready` แล้วแสดง toast "ปิดแล้วเปิดแอปอีกครั้ง"
- ไม่มี `.github/workflows` ในรีโป ไม่มี CHANGELOG ไม่มีโน้ตรุ่น deploy ทำมือด้วย `deploy.mjs`

## ต้นเหตุที่ทำให้ "refresh แล้วยังไม่ใหม่ทันที"
1. **Stale-while-revalidate ส่งของเก่าให้หน้าก่อนเสมอ** refresh ครั้งแรกหลัง deploy จึงเห็นรุ่นเก่า ครั้งที่สองถึงเห็นรุ่นใหม่
2. **Toast บอกให้ "ปิดแล้วเปิดแอป"** ทั้งที่ `skipWaiting` ทำให้ SW ใหม่ทำงานแล้ว ขาดแค่ให้หน้าโหลดซ้ำ
3. **ไม่มีตัวบอกเวอร์ชันที่เทียบได้** SW เทียบเนื้อไฟล์ทีละไฟล์ ไม่มีเลขรุ่นหรือโน้ตให้แสดง
4. **ไม่มีตัวเช็คอัปเดตตอนผู้ใช้เปิดแอปค้างไว้** SW เช็คเฉพาะตอนมี request

## ออกแบบ

### 1) ไฟล์รุ่น `release.json` (แหล่งความจริงเดียว)
สร้างตอน build ใส่ใน `build/web/release.json` ไม่แคชใน SW (ดึงด้วย `no-store`)
```
{ "build": "<digest เดียวกับ VERSION ของ sw.js>", "version": "0.2.0",
  "date": "2026-10-22", "notes": [ { "type": "new|improve|fix", "text": "..." } ] }
```
เลข `build` ตรงกับ VERSION ของ sw.js เสมอ จึงเทียบรุ่นได้โดยไม่ต้องเทียบเนื้อไฟล์

### 2) โน้ตรุ่นเขียนไว้ในรีโป
- `releases/<version>.md` หรือ `releases/notes.json` เขียนโดยคนหรือ AI ก่อน merge
- ชื่อไฟล์ไม่ใส่เลขเวอร์ชันซ้ำหลายฉบับ ใช้ไฟล์เดียว `releases/current.json` เป็นรุ่นล่าสุด และเก็บประวัติใน git ตามกฎชื่อไฟล์ของ Master
- build ต้องล้มถ้า build ใหม่แต่ `current.json` ไม่เปลี่ยน (บังคับให้ทุกอัปเดตมีโน้ต)

### 3) รีเฟรชครั้งเดียวได้ของใหม่ครบ (ไม่เรียลไทม์)
หลักการที่ Master สั่ง (22 ต.ค. 2026): ไม่มีการอัปเดตระหว่างใช้งาน ทุกอย่างอยู่รุ่นเดิมจนกว่าผู้ใช้จะรีเฟรชหรือเปิดแอปใหม่ ไม่มีปุ่มอัปเดต ไม่มีโหลดหน้าทับเอง

ต้นเหตุเดิมที่ต้องรีเฟรชสองรอบ: service worker ตอบไฟล์ชื่อคงที่ (css, react) จากแคชเก่าก่อนเสมอ HTML ใหม่จึงมาคู่กับไฟล์เก่า

วิธีแก้ (ปิดต้นเหตุที่จุดเดียวด้วยรหัสเนื้อหา):
- build คำนวณ **รหัสไฟล์** (`ASSET_V`) จากเนื้อหาไฟล์ชื่อคงที่ทั้งหมด (styles, fonts, vendor, js/react) ก่อน `next build` แล้วส่งให้ `layout.tsx` ใส่ต่อท้าย URL เป็น `?v=<รหัสไฟล์>` ตั้งแต่ต้นทาง (ห้ามแก้ HTML ทีหลัง เพราะ React จะ hydrate ไม่ตรง error #418)
- รหัสเดียวกันฝังใน `sw.js` (`ASSET_V`), `release.json` (`assets`) และ `window.__EV_BUILD__` ใน HTML; CI ตรวจว่าตรงกันทั้งสี่ที่
- `sw.js`: ไฟล์ที่ `?v=` ตรงรหัสไฟล์ = cache-first (เนื้อหาผูกกับรหัส เปลี่ยนไม่ได้) | หน้า HTML และ `release.json` = network-first (timeout 3 วินาที) | ไม่เรียก `skipWaiting` เอง
- รุ่นใหม่ติดตั้งเสร็จแล้ว "รอ" ผู้ใช้ที่กำลังใช้งานไม่ถูกทับ เมื่อผู้ใช้รีเฟรช หน้าใหม่ขอไฟล์ด้วย `?v=` ใหม่ ซึ่งไม่มีในแคชเก่า จึงดึงสดครบในรอบเดียว แล้วหน้าใหม่สั่ง `SKIP_WAITING` ให้ SW ใหม่รับช่วง

### 4) หน้าต่าง "มีอะไรใหม่" (What's New)
เป้าหมาย: บอกผู้ใช้อย่างเป็นทางการว่าเวอร์ชันนี้ปรับปรุง/เปลี่ยนแปลงอะไร แบบเดียวกับแพลตฟอร์มใหญ่ ไม่ใช่การแจ้งว่าระบบอัปเดตตัวเองสำเร็จ
- ใช้ชั้น dialog เดิมของแอป (ระบบ LAYERS) ให้โฟกัส/ปุ่มย้อนกลับทำงานถูก
- เนื้อหา: หัวข้อ "มีอะไรใหม่", เลขเวอร์ชัน+วันที่ (ไม่แสดงช่อง `-forge`), รายการโน้ตจัดกลุ่ม ใหม่/ปรับปรุง/แก้ไข, ปุ่มเดียว "เริ่มใช้งาน"
- ผูกกับ **เลขเวอร์ชัน** ไม่ใช่รหัสไฟล์: ขึ้นหนึ่งครั้งต่อเลขเวอร์ชัน จำด้วย localStorage `evarel.seenVersion` (แก้แค่ไฟล์โดยไม่ขยับเลขเวอร์ชัน = ไม่ขึ้น เพราะไม่มีอะไรใหม่ให้บอก)
- โน้ตที่แสดงต้องเป็นของเวอร์ชันที่หน้านั้นรันอยู่ (`__EV_VERSION__` ฝังใน HTML) กันขึ้นโน้ตของรุ่นอื่น
- ผู้ใช้ใหม่ครั้งแรกไม่เห็น (ไม่มีรุ่นก่อนให้เทียบ)
- ไม่มีปุ่มอัปเดต ไม่มีปุ่มไว้ทีหลัง ไม่ตรวจอัปเดตตามเวลา ไม่ดึงอะไรระหว่างใช้งาน

### 5) GitHub Actions เป็นตัวช่วย
- `.github/workflows/release.yml` ทำงานตอน push เข้า `develop` (forge) และตอนแท็กเข้า production
  1. ติดตั้ง รัน `npm test` และตัวตรวจ plan
  2. ตรวจว่า `releases/current.json` เปลี่ยนจากรุ่นก่อน (ไม่มีโน้ต = ล้ม)
  3. build ด้วย `build:web:forge` หรือ `build:web:production`
  4. deploy ผ่าน `wrangler` ด้วย secret `CF_API_TOKEN` ใน GitHub Secrets
  5. ตรวจหลัง deploy: ดึง `release.json` จาก URL จริง ต้องมี `build` ตรงกับที่เพิ่ง build
  6. สร้าง GitHub Release จากโน้ตรุ่น (ประวัติสาธารณะ ใช้เป็นฐานของหน้ารวมโน้ตรุ่นในแอปภายหลัง)
- production ผูกกับ environment ที่ต้องกดอนุมัติใน GitHub ก่อน (คงกติกา "ห้ามแตะ production โดยพลการ")

### 6) ฐานสำหรับแจ้งเตือนอัปเดตในแอป (ต่อภายหลัง)
- `release.json` + GitHub Releases เป็นฟีดรุ่น แอปอ่านรายการรุ่นย้อนหลังได้ (หน้า "มีอะไรใหม่" ในตั้งค่า)
- ต่อกับ Web Push ที่มีอยู่แล้วได้ ให้ Action ยิงแจ้งเตือน "มีเวอร์ชันใหม่" หลัง deploy สำเร็จ (ทำเป็นขั้นแยก เปิด/ปิดได้)

## ลำดับลงมือ (เมื่อ Master สั่ง)
1. `release.json` + `releases/current.json` + build ล้มเมื่อไม่มีโน้ต
2. SW: network-first สำหรับ navigation และ release.json
3. รีเฟรชครั้งเดียวได้ของใหม่ครบ (?v=รหัสไฟล์ + SW ไม่ skipWaiting เอง) + หน้าต่าง มีอะไรใหม่ ผูกเลขเวอร์ชัน
4. GitHub Actions: test, build, deploy forge, ตรวจหลัง deploy
5. production ผ่าน environment approval + GitHub Release
6. (ภายหลัง) หน้าประวัติรุ่น + push แจ้งอัปเดต

## ความเสี่ยงที่ต้องตัดสินใจ
- Network-first ทำให้เปิดแอปช้าลงเมื่อเน็ตแย่ (จำกัด timeout 3 วินาทีแล้วใช้แคช)
- `CF_API_TOKEN` ต้องอยู่ใน GitHub Secrets: ตรวจแล้ว (22 ต.ค. 2026) ว่า token GitHub ที่ Master เชื่อมไว้มีสิทธิ์ admin ของรีโป ผมเขียน Secret ได้เอง และมีค่า `CF_API_TOKEN` ใน `.env` ของผมแล้ว ไม่ต้องให้ Master ใส่ซ้ำ ผมจะขออนุญาตก่อนเขียนจริง (ยังไม่ได้เขียน รายชื่อ Secrets ตอนนี้ว่าง)
- ตอนนี้ deploy ทำจาก sandbox ผม ถ้าย้ายไป Actions แล้วต้องเลิก deploy มือ มิฉะนั้นรุ่นสองทางจะซ้อนกัน
- การบังคับ reload อาจทำข้อมูลที่กำลังกรอกหาย จึงไม่บังคับและใช้ปุ่มให้ผู้ใช้เลือก
