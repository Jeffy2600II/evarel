# แผนท่อบิลด์สำหรับกล่องใน app/pages/ (เสนอ Master ดูก่อนลงมือ)

สถานะ: **แผน ยังไม่ลงมือ** ไม่มีโค้ดถูกแก้ ข้อที่ระบุ "พิสูจน์แล้ว" มีหลักฐานรันซ้ำได้ใน [F4-snags.md](F4-snags.md) ส่วน "ข้อเสนอ" คือการตัดสินใจที่รอ Master

## 1. ท่อบิลด์วันนี้ (อ่านจากโค้ดจริง `scripts/build-react.mjs` 66 บรรทัด)

- งาน 1 ตัว = `runtime` (React ทั้งก้อน) + 1 ไฟล์ต่อหน้า จาก `app/src/react/*.jsx` ไป `app/web/js/react/<ชื่อ>.js` (iife, minify, ผลลัพธ์ commit ไว้ในรีโป)
- ไฟล์หน้าไม่มี React ในตัว ใช้ของ runtime ผ่าน `window.EvarelReact` และลงทะเบียนตัวเองท้ายไฟล์ด้วยบรรทัดแบบเดียวกันทุกหน้า
- ปลั๊กอิน `shared-via-runtime` สลับ import ของ `shared/tray.js`, `core/dates`, `core/schedule` ให้อ่านจาก global ของ runtime กันสำเนาซ้ำทุกหน้า
- `--check` เทียบผลบิลด์กับที่ commit ไว้ ต่างไบต์เดียวตก CI (`.github/workflows/web.yml` บรรทัด 45)
- ผู้บริโภคผลบิลด์ (ห้ามเปลี่ยนชื่อไฟล์หรือพาธ): `index.html` โหลด runtime/today/calendar/nav เป็น module, `19-views__settings` โหลดรายชื่อ `REACT_PAGES` 16 ชื่อตามชื่อไฟล์, `sw.js` แคช 17 รายการ `react/`, และ 15 ไฟล์ทดสอบกับสคริปต์อ้างพาธ `web/js/react/`

## 2. ปัญหา (พิสูจน์แล้ว)

1. กล่องที่เบ้าจูนสร้างผ่านเครื่องตรวจ แต่เติม `window.EvarelPages.x = ...` แล้วตก BOX-05
2. แค่ `const { h, Fragment } = window.EvarelReact;` หัวไฟล์ก็ตก BOX-05
3. ท่อบิลด์ไม่อ่าน `app/pages/` และ `build-css.mjs` ไม่รวม `.style.css` ของกล่อง (สไตล์กล่องยังไม่มีทางเข้าแอป)
4. BOX-06 ตรวจเฉพาะ import ที่ตกใน `app/pages/` ของกล่องอื่น การ import ถาดจาก `app/data` หรือ `app/shared` ไม่ผิดกฎ จึงไม่ต้องรื้อถาดเดิม 12 ไฟล์ในรอบนี้
   - หลักฐาน: สร้างกล่องด้วย `tuner.mjs` เติม `import ... from '../../data/zz.tray.js'` และ `'../../shared/zz.js'` รัน `checker.mjs` ผ่าน จากนั้นเติม import ไป `../probeb/ProbebPage.jsx` (กล่องอื่น) ตก `[BOX-06]`

## 3. ข้อเสนอ: ให้บิลด์เป็นฝ่ายต่อสิ่งที่กล่องห้ามเขียนเอง

กล่องเขียนแต่ของของตัวเอง ส่วนบรรทัดที่แตะ `window` บิลด์ฉีดให้ตอนห่อ

**กล่องมีหน้าที่:** `export default` ฟังก์ชันหน้า (props เข้า คืน element) และ export ฟังก์ชันเตรียม props ถ้ามี
**บิลด์ฉีดให้:** (ก) ตัวรับ `h`/`Fragment` จาก `window.EvarelReact` (ข) บรรทัดลงทะเบียน `window.EvarelPages.<ชื่อ>` และ `window.EvarelComponents.<ชื่อ>` (ค) ชื่อ `<ชื่อ>` มาจากชื่อโฟลเดอร์กล่อง

เพื่อให้ผลลัพธ์**ไบต์เดียวกับวันนี้** ตัวห่อต้องผลิตรูปเดิม `window.EvarelPages=window.EvarelPages||{};window.EvarelPages.stats=a=>window.EvarelReact.renderToStaticMarkup(...)` ไม่ใช่รูปใหม่ที่ใกล้เคียง

## 4. ลำดับงานที่เสนอ (เล็กไปใหญ่ แต่ละขั้นมีตัวตรวจก่อนไปขั้นถัดไป)

| ขั้น | ทำอะไร | แตะท่อเดิมไหม | ตัวตรวจที่ต้องผ่าน |
|---|---|---|---|
| A | เพิ่ม **งานบิลด์ที่สอง** แยกจากลูปเดิม อ่านเฉพาะ `app/pages/*/` ผลลัพธ์ชื่อไฟล์เดียวกับของเดิม | ไม่ (เพิ่มต่อท้าย ลูปเดิมไม่เปลี่ยน) | `--check` ของ 17 ไฟล์เดิมยัง **ตรงทุกไบต์** ตอนที่ `app/pages/` ว่าง |
| B | ตัวห่อกล่อง: ฉีด (ก) (ข) แล้วเทียบกับ `stats.js` เดิมด้วยกล่องทดลองนอกรีโป | ไม่ | ผลบิลด์ของกล่องทดลองที่เนื้อหาเท่า `stats.jsx` ต้อง **ตรงไบต์** กับ `stats.js` เดิม |
| C | ตัดสินว่า stats/all ย้ายแล้ว ไฟล์ซอร์สเดิมใน `app/src/react/` ถูกลบพร้อมกัน (ห้ามค้างสองชุด) | แตะ (ลบซอร์สสองไฟล์) | `--check` ตรง, `stats_html_equiv`, ประตูภาพ 30/30 และ errs 0 |
| D | ต่อ `.style.css` ของกล่องเข้า `build-css.mjs` | แตะ `build-css.mjs` | ภาพ 30/30 ที่ 0 พิกเซล (สไตล์กล่องว่างต้องไม่ทำให้ `app.css` ต่างไบต์) |

ขั้น A และ B ไม่มีผลต่อแอปที่ใช้งานเลย (เพิ่มงานบิลด์ที่ไม่มีกล่องให้อ่าน) จึงย้อนง่ายและเป็นจุดตัดสินใจที่ปลอดภัยที่สุดก่อนขั้น C

## 5. ความเสี่ยงที่ผมเห็น

- **รูปห่อต้องตรงไบต์:** ถ้าห่อต่างไป `--check` ตกทุกครั้ง (ดีที่มีตัวจับ) แต่ถ้า minify จัดเรียงตัวแปรต่างไป ต้องยอมรับว่าไฟล์ผลลัพธ์ของสองหน้าเปลี่ยนไบต์ได้ และพิสูจน์ด้วยตัวเทียบพฤติกรรมแทน ซึ่งเป็นเกณฑ์ที่หลวมกว่า ต้องให้ Master เลือกว่ายอมไหม
- **ไฟล์ทดสอบ 15 ไฟล์อ้างพาธผลบิลด์:** ชื่อไฟล์ผลลัพธ์ต้องคงเดิม มิฉะนั้นต้องแก้ทดสอบทั้งชุด
- **ลำดับโหลด:** กล่องที่ย้ายต้องยังถูกโหลดตามลำดับเดิมของ `REACT_PAGES` (runtime ก่อนเสมอ)
- **`sw.js` แคช:** ชื่อไฟล์คงเดิมจึงไม่ต้องแตะ ถ้าเปลี่ยนชื่อต้องยกเลขแคช (ผมยังไม่ได้ตรวจรายละเอียดกลไกยกเลขแคชของ sw.js)

## 6. สิ่งที่ผมยังไม่ได้ตรวจ

- ยังไม่ได้ลองเขียนตัวห่อจริง จึงยังไม่รู้ว่า minify จะให้ไบต์ตรงหรือไม่ (ขั้น B คือการหาคำตอบนี้)
- ยังไม่ได้ตรวจว่า `.style.css` ของกล่องควรรวมเข้า Tailwind หรือต่อท้ายหลัง build (ขั้น D ต้องดูอีกรอบ)
- ยังไม่ได้วัดจำนวนขั้นตอนเพิ่มหน้าใหม่ด้วยเบ้าจูน (F4 ผลลัพธ์ข้อ 6)

## 7. สิ่งที่ต้องการให้ Master ตัดสิน

1. เห็นด้วยกับหลัก "บิลด์ต่อบรรทัดที่แตะ window ให้ กล่องไม่เขียนเอง" หรือไม่
2. ถ้าห่อแล้วไบต์ไม่ตรง 100% ยอมใช้ตัวเทียบพฤติกรรมแทนได้ไหม หรือให้ปรับห่อจนตรงไบต์เท่านั้น
3. อนุมัติให้เริ่มขั้น A และ B (ไม่กระทบแอปที่ใช้งาน) แล้วหยุดรอผลก่อนขั้น C
