# แผนเสริม: โรงงาน Frontend ของ Evarel

กฎของไฟล์นี้เหมือนแผนหลัก: ห้ามมีวิธีทำ ห้ามมีโค้ด ห้ามมีค่าตั้งค่า มีเพียง ขั้น เป้าหมาย ผลลัพธ์ที่ตรวจได้ สถานะ และลิงก์ไปไฟล์ลึก
แผนนี้เป็นแผนเสริมของ [MASTER-PLAN.md](MASTER-PLAN.md) ความหมายของคำว่าเสริม (Master ยืนยัน 26 ต.ค. 2026): เป็นแผนเพิ่มเติมที่ไม่มีอยู่ในแผนเดิม ทุกอย่างในแผนเดิม (S0 ถึง S7 ลำดับ เกณฑ์ ข้อตัดสินใจ) ยังเหมือนเดิมทุกประการ แผนนี้ไม่แก้ ไม่เลื่อน ไม่สลับขั้นเดิมใดๆ เพียงเพิ่มงานตามแนวคิดโรงงานเข้ามาเป็นชั้นเสริม เมื่อมีจุดที่ดูเหมือนขัดกัน ให้ถือว่าแผนเดิมชนะและหยุดถาม Master
ที่มา: เอกสารรวมโรงงาน Frontend Evarel (ไฟล์ที่ Master แนบ 26 ต.ค. 2026) + ตัวเลขที่วัดจากรีโปจริง ณ commit c738cf1 บนสาขา develop

## 1. เป้าหมายเดียว

**ผู้ใช้เห็นหน้าตาและพฤติกรรมเหมือนเดิมทุกพิกเซล แต่โค้ด Frontend ถูกจัดใหม่เป็นโรงงาน: หน้าหนึ่ง = กล่องหนึ่ง, ชิ้นส่วนกลางจุดเดียว, ค่าดีไซน์จุดเดียว, ข้อมูลเข้าทางถาดเดียว, และเครื่องมือเป็นคนบังคับกติกา ไม่ใช่ความจำ**

ผลที่ต้องได้ (ตรงกับที่ Master ต้องการ: พัฒนาง่าย เร็ว เป็นระบบ คาดเดาได้ ทั้ง agent และนักพัฒนามนุษย์):
- เพิ่มหน้าใหม่ด้วยคำสั่งเดียว ได้กล่องครบสามชั้นพร้อมใช้
- รู้ก่อนแก้ว่ากระทบหน้าไหนบ้าง
- กติกาไม่ผ่าน = สายพานไม่ปล่อย พร้อมบอกว่าผิดข้อไหนเพราะอะไร

## 2. ทิศทางที่ล็อกแล้ว (มาจาก Master ในเอกสารโรงงาน ไม่ตัดสินใหม่)

- แนวทางโรงงาน 9 หัวข้อคือข้อสรุปจบ ไม่วางแผนแนวคิดใหม่
- ลำดับแนวคิด: กล่องฟีเจอร์ (ข้อ 1) > โกดังแบ่งโซน (ข้อ 2) > แม่พิมพ์กลาง (ข้อ 3) > ถาดข้อมูล (ข้อ 4)
- แผนที่ระบบเป็นแบบอัตโนมัติ (GitHub Actions) กดลิงก์เข้าไฟล์จริงได้ สร้างฟีเจอร์ใหม่ผ่านเบ้าจูนคำสั่งเดียว
- ชื่อไฟล์และโฟลเดอร์ห้ามมีเลขเวอร์ชัน
- งานเว็บซับซ้อนต้องรัน Graphify ตั้งแต่ต้น
- ศัพท์ในโค้ดใช้ศัพท์มาตรฐานวงการ (features, tokens, contracts) ศัพท์โรงงานใช้คุยกัน (ข้อเสนอในเอกสาร ยังรอ Master ยืนยันทีละคำ ดูข้อ 7)
- ทำบน develop เท่านั้น ห้ามแตะ main และ production (กฎเดิมที่ยังมีผล)

## 3. การตีความที่ผมต้องเขียนให้ชัด (จุดที่เอกสารโรงงานกับคำสั่งรอบนี้ดูขัดกัน)

เอกสารโรงงานบอก "ห้ามยึดโครงระบบเดิมของ Evarel เป็นฐาน" ส่วนคำสั่งรอบนี้บอก "เสริมจากแผนเดิม ผู้ใช้เห็นเหมือนเดิม" ผมตีความดังนี้ **(การตีความของผม ต้องให้ Master ยืนยัน ดูข้อ 7 ข้อ D1)**:
- โครงปลายทางออกแบบจากแนวคิดโรงงาน ไม่ลอกโครง `app/src/{core,m,react}` เดิม
- เส้นทางไปปลายทางคือ ย้ายของเดิมเข้ากล่องทีละกล่อง โดยพิสูจน์ความเท่าเดิมด้วยประตูเดิม (วิธีเดียวกับที่ S4 ทำสำเร็จ)
- ไม่เขียนหน้าใหม่ทับหน้าเก่า ไม่ใช้ตัวแปลงอัตโนมัติ

## 9. ถ้าเวลาไม่พอ

- ทั้งแผน F เลื่อนได้ทั้งก้อน เพราะแอปทำงานเหมือนเดิมอยู่แล้ว ไม่กระทบหมุดหมาย 5 เกณฑ์ (การตัดสินเป็นของ Master เสมอ)
- ถ้าต้องตัด: ตัด F6 ก่อน (หน้าเก่าอยู่ที่เดิมได้) แล้ว F5 แต่ F1-F2 มีค่าแม้ไม่ครบ
- F2 ต้องมาก่อน F4 เสมอ (เครื่องยังไม่มี โรงงานไม่หมุนเร็ว ตามเอกสารโรงงาน B8)

## 10. สิ่งที่ยังไม่ทราบ (ต้องวัดก่อนอ้างเป็นข้อเท็จจริง)

- เวลาที่ใช้จริงของแต่ละขั้น ยังไม่เคยวัด
- ตัวเลข `window` ข้างต้นเป็นการนับข้อความดิบ ต้องแยกอ่าน/เขียน/คอมเมนต์ใน F1
- กล่อง 1 ใบควรมีกี่บรรทัดจึงเรียก "ล้น" ยังไม่มีข้อมูล ต้องได้จากกล่องนำร่อง (F4)
- ผลของ 6 กลไกเสริมต่อคะแนน ยังไม่ได้ประเมินเป็นระบบ (ตามเอกสารโรงงานระบุไว้เอง)
- CI รัน X-ray ตรวจรายหน้าภายในเวลาและโควตาฟรีของ GitHub Actions ได้หรือไม่ ยังไม่ได้วัด
